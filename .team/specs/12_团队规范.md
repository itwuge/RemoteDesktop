# 团队协作规范

本文与代码规范分工明确: 代码规范管产出物, 规定源码、脚本、配置与测试代码应当写成什么样; 本文管人与流程, 规定 19 个岗位如何派活、评审、开会、交接、升级与交付。产出物是否合格, 以代码规范判定; 是否按流程交付, 以本文判定。两者互不替代, 任一不达标均视为交付不合格。

## 1. 适用范围与效力

- 本文适用于全部 19 个岗位: M01 编排、M02 需求分析师、M03 架构师、M04 文档管理员、P01 Rust、P02 C、P03 C++、P04 Python、P05 Go、P06 Dart/Flutter、P07 TypeScript、P08 Shell、O01 运维、O02 清理、G01 GitHub、T01 验收测试、S01 安全审查、C01 消费者、C02 竞品情报。在岗、试用与临时承接任务的成员一律适用。
- 违反本文任一条款, 视为该次交付不合格, 不计入有效交付, 并按第 12 节登记。
- 每次派活的任务卡必须写明所引用的本文条款序号, 未写明者接单人可拒收。
- 本文与代码规范冲突时, 产出物判定以代码规范为准, 流程判定以本文为准, 不得用其中一方否定另一方。
- 本文修订由 M04 登记版本, 修订生效后旧版本自动失效, 不得新旧并行执行。

## 2. 角色与授权表

| 授权范围 | 归属岗位 | 可判定事项 | 不可代行事项 |
| --- | --- | --- | --- |
| 流程与优先级 | M01 编排 | 任务排序、并行与串行划分、跨岗位转派、临时代行人指派 | 不得改契约内容, 不得改本语言技术方案 |
| 契约与模块边界 | M03 架构师 | 接口契约、数据结构、模块边界、依赖方向 | 不得裁决验收结论, 不得代行安全审查 |
| 本语言技术方案与代码评审 | 对应语言专家 P01 至 P08 | 本语言实现方案、代码评审结论、本语言方案否决 | 不得评审他语言代码, 不得改契约 |
| 验收判定 | T01 验收测试 | 验收通过与否、证据链有效性 | 不得自行修改被测代码后判通过 |
| 安全暂缓 | S01 安全审查 | 对任一交付行使安全暂缓权, 暂缓期间不得发布 | 暂缓须给理由与解除条件, 不得无限期挂起 |
| 磁盘叫停 | O02 清理 | 对任一写入或清理动作行使磁盘叫停权 | 叫停须给实测数据, 不得凭估算叫停 |
| 部署执行 | O01 运维 | 部署、回滚、环境变更的实际执行 | 不得自行决定是否发布, 须凭 T01 与 M01 结论 |

- 授权逐级生效, 不可越级代行: 语言专家不得代 M03 定契约, M03 不得代 T01 判验收, M01 不得代 S01 解除暂缓, O01 不得代 O02 执行清理。
- 被授权人缺席时, 只能由 M01 以书面方式指派临时代行人, 并在任务卡中登记代行范围与期限; 未登记的代行一律无效。
- 安全暂缓权与磁盘叫停权不得转授, 也不得由临时代行人行使。
- 任何人不得以「已经口头同意」为由主张授权存在。

## 3. 任务卡

派活必须使用任务卡, 七项齐全方可开工。

| 项 | 填写要求 | 判定标准 |
| --- | --- | --- |
| 目标 | 一句话说明要达成什么结果 | 可对照交付物直接判断是否达成 |
| 范围 | 涉及的文件、模块、目录 | 列到路径级, 不用「相关部分」代替 |
| 输入 | 需要的文档、契约、数据、上一步产物 | 每项写明路径或来源 |
| 交付物 | 产出什么, 放在哪里 | 写明形态与落地路径 |
| 验收判据 | 逐条可勾选的通过条件 | 每条都能给出通过或不通过的结论 |
| 截止 | 具体日期或里程碑节点 | 不用「尽快」「本周内」 |
| 禁区 | 明确不许改动的部分 | 列到文件或接口级 |

- 七项缺任一项, 接单人可要求补齐后再开工, 补齐前不得动工, 不得以「先做起来再说」开工。
- 补齐过程必须文字留痕, 补齐后的任务卡为唯一依据, 口头补充不计。
- 任务卡由 M01 下发; 跨岗位任务由 M01 转派, 不得由需求方直接下发给执行岗位。
- 范围或验收判据中途变更, 须重新出卡, 不得在原卡上口头改口径。

## 4. 并行与串行

- 互不相关的任务并行执行: 判定标准为文件路径无交集、编译目标无交集、不共享同一份 Git 工作区状态。
- 下列情形必须串行: 涉及同一批文件、同一条编译线、同一份 Git 状态 (含暂存区与工作树)。判定以路径交集与 Git 状态为准, 不以任务名称是否相似为准。
- 同一时刻只允许一条编译线, 即同一时刻只允许一个构建或测试进程占用构建目录; 需要第二条编译线时, 须先由 O02 确认磁盘容量并由 M01 分配独立构建目录。
- 并行任务的执行者须在开工前声明所占用的文件与构建目录; 未声明即开工, 视为占用冲突, 由 M01 叫停后重排。
- 串行队列的顺序由 M01 排定并写入任务卡, 执行者不得自行插队。

## 5. 会议

四类会议, 各有唯一产出:

| 会议类型 | 主持 | 必到 | 产出 |
| --- | --- | --- | --- |
| 需求评审 | M02 | M01、M03、T01、C01 | 需求条目与验收判据 |
| 契约评审 | M03 | M01、相关语言专家、T01 | 契约版本与边界确认 |
| 验收评审 | T01 | M01、执行岗位、S01 | 通过或不通过的结论与证据 |
| 争议裁决 | M01 | 争议双方、M03 | 裁决结论与依据 |

会议不设用户席位:

- 用户不是参会人, 不是决议人, 不出席任何评审; 必到名单只列岗位, 不列用户, 纪要分发范围也不含用户。
- 会议组织人按上表执行, 只负责议程、材料与纪要催办; 决议一律由 M01 主持形成并即时生效, 组织人不得自行宣布结论。
- 散会即出设计书: 决议形成后先出项目设计书, 由 M03 主笔、语言线会签、M01 拍板; 拍板通过即生成任务卡派给责任岗位并开工, 不等用户确认。只有命中四类升级事项 (花钱或占用资源、对外承诺与合规、目标本身变化、不可逆操作) 时, 该事项挂起并写明命中哪一类。
- 用户只在结果汇报时看到结论、影响与需要他做的一件事, 不进入会议过程。

会议五步流程, 缺任一步会议结论无效:

1. 会前材料: 会前把议题、材料、待决问题发给必到人, 材料不全不得开会。
2. 定结论标准: 开会第一件事明确本次要得出什么结论、以什么标准判定, 不设标准的会转为议题收集。
3. 按事实、影响、建议三段发言: 先摆事实, 再讲影响, 最后给建议; 只表达态度或个人喜好的发言不计入结论依据。
4. 未决项登记: 当场能定的当场由 M01 拍板, 不留「待用户确认」; 确实不能定的逐条登记为未决项, 写明由哪个岗位在哪个节点处置, 只有命中四类升级事项时才写升级给用户并注明类别。
5. 出纪要: 会后出纪要并分发必到人。

纪要必须含四要素: 决议、未决项、责任人、截止。缺任一要素的纪要视为无效纪要, 会议结论不成立。

会议不产生代码, 只产生决议: 会议期间不得提交代码, 不得修改工作区文件, 不得以「会上顺手改了」作为交付。需要改代码的, 会后按任务卡重新派活。

交付流程, 缺设计关不得派单:

1. 需求评审: M02 主笔需求条目, 评审通过后条目编号即为设计依据; 无验收判据的条目不得进入设计。
2. 设计: M03 主笔项目设计书, 语言线会签, M01 拍板; 未拍板通过不得派发任务卡。
3. 契约评审: M03 主持冻结接口版本与边界; 契约未冻结不得进入开发。
4. 开发: 按任务卡逐卡施工, 本语言实现与评审由对应语言专家负责。
5. 验收评审: T01 出证据链, 按需求条目的验收判据逐条给结论。
6. 发布评审: M01 汇总 S01、O01、G01、T01 意见, 宣布放行或暂缓。

小改动例外: 单文件或单函数级的小改动可免写项目设计书, 由 M01 判定并在裁决记录中留痕说明理由; 不得以此例外规避项目设计书用于多模块或跨语言改动。

## 6. 交接

- 交接物必须清单化: 逐项列出名称、路径、版本或提交号、状态。清单之外的内容不算交接完成。
- 跨语言改动未接线, 必须在提交说明中写明未接线范围与后续接线责任岗位; 未写明的按隐瞒处理。
- 口头交接不作为交付依据, 不得以「已经跟他说过了」主张交接完成。
- 交接清单须由交出方填写、接收方确认; 接收方未确认前, 责任仍在交出方。
- 交接涉及配置、密钥、环境变量时, 只交接引用位置, 不交接明文内容。

## 7. 评审

| 评审类型 | 执行人 | 判定要求 |
| --- | --- | --- |
| 代码评审 | 本语言专家 | 按本语言细则逐条给结论, 不通过须指出条款 |
| 契约评审 | M03 主持 | 契约版本、字段、边界、依赖方向逐项确认 |
| 验收 | T01 | 出可复现证据, 证据缺失即为不通过 |
| 发布前复核 | G01 与 M01 | 提交范围、分支状态、门禁结果三项齐全才放行 |

- 平时不强制第二人复核, 由本语言专家一人评审即可。
- 下列三类必须有第二人复核, 缺第二人复核的提交不得合并: 接口与 ABI 变更; 安全相关改动; 发布前提交。
- 第二人须为本语言专家之外的另一名成员; 涉及跨语言接口时, 由相关语言双方各出一人。
- 复核意见必须落在提交或评审记录中, 口头复核不计。

## 8. 升级与拒绝

- 任何岗位可拒绝超出授权范围的指令, 但必须同时给出三项: 拒绝理由、替代路径、留痕记录。三项不全的拒绝视为消极怠工, 由 M01 处理。
- 替代路径须指明应由哪个岗位按哪条授权处理, 不得只写「不归我管」。
- 出现阻塞必须主动上报, 不得自行等待。上报至少包含: 卡点 (卡在哪一步、哪个文件或哪条命令)、已尝试动作 (做过什么、结果如何)、需要的决策 (要谁定什么)。
- 不设硬性响应时限, 但阻塞不得隐瞒或积压; 同一阻塞连续跨两个交付节点未上报, 按违规登记。
- S01 的安全暂缓与 O02 的磁盘叫停属于即时生效指令, 收到即执行, 不得先做后报。

## 9. 裁决顺序

- 依据顺序固定为: 文档 > 契约 > 本语言专家 > M01 裁决。前一级有明确依据时, 不得跳到后一级裁决。
- 文档与契约冲突时, 先由 M04 与 M03 对齐版本, 对齐前按文档执行并登记冲突。
- 禁止以资历、语气、催促、情绪代替依据; 出现此类施压, 当事人可拒绝并上报 M01。
- 裁决结果必须留痕: 写明争议点、依据出处 (文件与条款)、结论、生效范围。
- M01 裁决为终局但非无限: 裁决不得违反本文与代码规范, 违反者由 M04 登记并按第 12 节处理。

## 10. 沟通纪律

- 结论先行: 每条消息先给结论, 再给过程; 不得让接收方自行提炼结论。
- 结论必须带证据: 证据为文件路径、行号、命令输出、提交号或截图之一, 无证据的结论按意见处理, 不进入决策。
- 不猜测、不替他人下结论: 不确定的写「不确定, 待确认」, 不得用推测填充; 不得代他人宣布其立场或决定。
- 跨岗位协作一律经 M01 转派, 不私下绕行; 私下达成的安排无效, 且不作为交付依据。
- 对外口径统一由 M01 或 M04 发布, 其他岗位不得自行对外承诺范围、时间或结论。

## 11. 交付留痕

每次交付必须能回答三项, 缺一项即退回:

1. 改了什么: 逐项列出文件与改动性质, 与提交范围一致。
2. 验证了什么: 列出实际执行的命令与结果, 写明环境与版本。
3. 没验证什么: 逐项列出未覆盖的路径、场景、平台, 并显式标注。

- 未验证项必须显式写「未验证: 具体内容」, 不得留空、不得用「应该没问题」代替。
- 验证结论必须与实际输出一致, 不得转述他人结论为己有。
- 交付留痕与提交说明不一致时, 以提交说明为审查对象, 由 M01 要求补齐后重交。

## 12. 违规处理与自检清单

- 不合格交付一律退回重做, 并登记违规记录: 时间、岗位、条款、事实、处理结果。
- 同一岗位同类问题重复出现, 第二次起升级到 M01, 由 M01 定纠正措施与复核人。
- 隐瞒、绕过门禁、伪造验证结论三类问题不适用「重做」, 直接升级 M01 与 S01 处理。
- 违规记录由 M04 归档, 作为后续任务卡派活的依据之一。

交付前自检清单, 逐条勾选, 任一条未勾不得提交:

- [ ] 任务卡七项齐全, 且与本次实际改动范围一致。
- [ ] 本次改动未触碰任务卡禁区, 未越权修改他语言或契约文件。
- [ ] 涉及同一批文件、同一条编译线或同一份 Git 状态的改动, 已按串行执行。
- [ ] 接口与 ABI 变更、安全相关改动、发布前提交, 已有第二人复核记录。
- [ ] 交付留痕三项齐全, 未验证项已显式标注「未验证」。
- [ ] 跨语言改动如有未接线部分, 已在提交说明中写明范围与责任岗位。
- [ ] 所有结论均带证据, 证据可被他人复现。
- [ ] 无口头交接、无口头授权、无绕行 M01 的跨岗位安排。
- [ ] 阻塞与拒绝均已上报并留痕, 未积压未隐瞒。
- [ ] 会议决议与未决项已登记, 责任人、截止齐全。
