# 代码规范总则

## 1. 适用范围与效力

- 本总则适用于本项目全部语言的源码、脚本、构建配置与测试代码。
- 各语言细则与本总则同时生效; 细则与本总则冲突时, 以本总则优先, 并由该语言专家提交细则修订。
- 所有语言专家产出的代码必须符合本总则与对应语言细则。不符合者不予评审通过, 不得进入验收与发布环节。
- 语言细则文件:

| 序号 | 文件 | 覆盖范围 |
| --- | --- | --- |
| 01 | 01_Python.md | Python 脚本与工具代码 |
| 02 | 02_Rust.md | Rust 系统层与库代码 |
| 03 | 03_C.md | C 源码与 C ABI 导出面 |
| 04 | 04_CPP.md | C++ 模块与 C++ 封装层 |
| 05 | 05_Go.md | Go 服务、CLI 与并发代码 |
| 06 | 06_Dart.md | Dart 与 Flutter 客户端代码 |
| 07 | 07_TypeScript.md | TypeScript 前端与 Node 侧脚本 |

## 2. 文件头

每份源码文件首部必须有一个固定栏目的头部注释块, 栏目固定八项, 缺一项即判不合格。

| 栏目 | 填写要求 |
| --- | --- |
| 文件 | 文件名含扩展名, 不含路径 |
| 所属目录 | 相对仓库根的目录, 以 `/` 结尾 |
| 文件用途 | 一句话说明该文件解决什么问题, 面向什么输入产出什么结果 |
| 架构定位 | 属于哪一层, 上下游分别是谁, 依赖方向朝哪边 |
| 核心功能 | 该文件对外提供的功能点, 逐项列出, 不写实现细节 |
| 职责边界 | 明确不做什么, 防止职责扩散, 写清边界上的取舍 |
| 运行环境 | 语言与运行时版本, 可运行的平台与前置条件 |
| 依赖关系 | 上游依赖谁, 下游谁调用, 有无可选依赖 |

要求:

- 八栏顺序固定, 不得增删栏目、不得改名、不得合并同类项。
- 栏目内容必须写实, 禁止「见 README」「同上」「详见设计文档」这类转指; 需要引用其他文件时写明路径。
- 注释形式由各语言细则规定, 但栏目名、栏目顺序、栏目语义必须与本总则一致。
- 文件头必须位于文件第一个有效声明之前, 中间不得插入其他注释或代码。
- 禁止在文件头写作者、日期、修改历史、版本日志。

各语言文件头写法:

| 语言 | 写法 |
| --- | --- |
| Python | `# ====` 上下边框包住八栏, 栏间用 `# ----` 分隔, 单栏形式 `# 文件        : name.py` |
| Rust | `//!` 模块文档注释, 首行写模块定位, 空行后八栏逐行 `//! 文件: name.rs` |
| C | `/* */` 块注释 banner, `@file` 对「文件」栏, `@brief` 对「文件用途」栏, 其余六栏逐行书写 |
| C++ | 同 C; 类与模板的说明在类型注释处补充, 文件头八栏不重复类职责 |
| Go | 包注释 `// Package xxx ...` 写包用途, 其余八栏以 `//` 结构化字段逐行列出 |
| Dart | `///` 文档注释块, 库入口置于 `library;` 之上, 其余文件置于首个 `import` 之前 |
| TypeScript | `/** */` JSDoc 块, 位于全部 `import` 之前 |
| Shell | shebang 之后 `#` 注释块, 除八栏外必须写输入、退出码、依赖命令 |

## 3. 导入/依赖区

- 分组顺序固定: 语言标准库 / 第三方 / 本项目内部, 组间空一行。
- 每一行注明来源与用途: 来源写标准库名、第三方包名或项目内模块路径, 用途写该引入支撑的具体功能。
- 禁止无意义引入: 未使用的 `import` / `include` / `use` / `require` 必须删除, 不得留在文件里等以后用。
- 通配引入、点导入、匿名导入、整包引入必须有同行原因注释, 无原因即不合格。
- 能用单符号引入的不引整模块; 能从子模块引入的不引根包。
- 条件依赖、平台依赖必须在同组末行注明生效条件与关闭后的退化行为。

各语言写法:

- Python: 行尾 `#` 注释, 标准库与项目内分组, 例 `import json  # 标准库: JSON 解析`。
- Rust: `use` 行尾 `//` 注释, `std` / 外部 crate / `crate` 内部分组, 禁止 `use foo::*`。
- C: `#include` 顺序为对应头文件 / 标准库 / 第三方 / 项目内, 每行行尾注释来源与用途。
- C++: 同 C, 另加前置声明区与模板显式实例化声明, 各段分别注释。
- Go: `import` 块内每行尾 `//` 注释, 禁止点导入 `.`, 匿名导入 `_` 必须写注册副作用。
- Dart: `import` 行尾 `//` 注释, 相对路径与 `package:` 分两段。
- TypeScript: `import` 行尾 `//` 注释, 纯类型使用 `import type`, 不得混入运行时依赖。
- Shell: `source` / `.` 引入行、外部命令依赖清单, 行尾 ` #` 注释来源与用途。

## 4. 类型与函数注释

每条类型注释与函数注释必须写清四件事:

1. 用途: 这个类型或函数解决什么问题, 在调用链上处于什么位置。
2. 参数: 每个参数的含义、类型、取值约束、可空性、单位。
3. 返回值: 含义、可空性、失败时返回什么、哨兵值是什么。
4. 异常与错误: 可能抛出的异常或返回的错误, 逐条写触发条件。

只写「做什么」不算合格, 必须写「为什么这样做」: 设计取舍、约束来源、失败处理策略的依据、为什么不用另一种更常见的写法。

- 类型: 导出的类、结构体、枚举、接口、联合类型、类型别名必须有注释; 私有类型至少一行说明用途, 不允许空注释。
- 函数: 导出函数必须有注释; 私有函数超过 10 行、含副作用、含边界处理时同样必须有。
- 字段与成员: 导出类型的字段逐项注释; 枚举成员逐项注释。
- 一致性: 代码变更必须同步修改注释; 代码改了注释没改视为不合格。
- 禁止: 复述类型名或函数名、空注释、用 TODO 代替说明、用注释掩盖命名不当。

## 5. 编辑器可见性要求

注释不只服务于通读代码, 也是编辑器里的第一手信息, 分工必须明确:

- 类注释用于鼠标悬停类名时查看: 这个类的定位、一次典型调用的工作流程、实例属性清单、构造参数。
- 方法注释用于鼠标悬停方法名时查看用途, 并在输入参数时提供参数提示: 参数名、含义、单位、可空性。
- 属性补全与类型提示来自真实的类型注解, 不来自 docstring: docstring 里的 `:type:` 只是文档, 编辑器不会据此推断类型。

因此规定三件事, 缺一即不合格:

1. 必须写真实类型注解: 参数、返回值、实例属性都要有语言层面的类型标注, 不能只把类型写在 `:type:` 或注释文字里。
2. 每个公开方法必须有完整 docstring: 用途、参数、返回值、异常, 缺项即不合格。
3. 实例属性必须在 `__init__` 中带类型标注(如 `self.rules: dict[str, str] = ...`); 不在 `__init__` 赋值的属性, 须在类体上声明类型。

各语言落地方式:

| 语言 | 类型注解载体 | 悬停信息来源 |
| --- | --- | --- |
| Python | 函数签名注解 + `__init__` 内属性注解 | 类 docstring 与函数 docstring |
| Rust | 签名类型 + 结构体字段类型 | `///` 文档注释 |
| C | 原型声明 + 结构体成员类型 | Doxygen 注释 |
| C++ | 签名类型 + 类成员类型 | Doxygen 注释 |
| Go | 签名类型 + 结构体字段类型 | `//` 注释 |
| Dart | 签名类型 + 字段类型 | `///` 文档注释 |
| TypeScript | 签名类型 + 字段类型 | JSDoc |
| Shell | 无类型系统, 靠注释与 `local` 声明 | 函数上方 `#` 注释 |

## 6. 行尾注释判据

- 行尾注释只写原因, 不写翻译: 回答「为什么这么写」「改错会怎样」, 不复述语句在做什么。
- 判据: 一行代码如果「看起来显然但改错会有后果」, 必须写一行行尾注释。典型情形:

| 情形 | 说明 |
| --- | --- |
| 边界与兜底 | 空值归一、超时截断、取不到就返回默认值、上限截断 |
| 顺序与时机 | 先后依赖、必须提前或延后执行、初始化次序 |
| 魔数与特例 | 硬编码阈值、某个平台或站点的特例、协议要求的固定值 |
| 有意差异 | 与同目录其他实现不同且不能统一, 必须写明原因 |
| 安全性 | `unsafe`、强制转换、指针所有权转移、权限边界 |
| 静默失败 | 有意吞掉异常、忽略错误码、忽略退出码 |

- 免写情形: 声明、纯转发、显然的赋值与返回, 且改错不会有后果。
- 长度: 一行内写完; 需要多行解释的, 改为函数注释或就近块注释。
- 禁止: 用行尾注释记录调试残留、注释掉的旧代码、待办占位。

## 7. 分区标记

- 统一形式: 注释符 + `=========` + `**` + 分区名 + `**` + `=========`, 例如 Python 写 `# =========** 模块级常量 =========**`。
- 标记的下一行必须是该类型的说明注释: 有文档注释的语言写文档注释首行, 无文档注释的语言写一行职责说明。
- 标记本身只负责跳转定位, 不重复说明内容: 不写「下面开始定义 xxx」「本段包含 xxx」这类叙述。
- 分区名使用文件内的实际概念: 常量、类型、函数、入口、测试; 不使用序号或空泛词。
- 分区之间空一行; 建议顺序为常量 -> 类型 -> 函数 -> 入口 -> 测试。
- 单类或单函数文件同样必须写分区标记, 保持全仓一致。
- 一个分区内的代码必须同类同层级, 不允许把常量与函数混在同一分区。

## 8. 标点与空格（强制）

### 8.1 强制条款

- 注释与 docstring 中, 逗号、冒号、分号、括号、引号、句号一律半角。
- 中文与英文或数字之间必须留一个半角空格, 例: `签到成功 3 个账号`, `读取 state.json 失败`。
- 代码行内不得出现全角标点: 字符串字面量内部除外, 标识符、运算符、注释一律半角。
- 仅字符串内容本身需要时才用全角, 例: 站点文案原样保留 `logger.info("签到成功, 收益 +5")` 中的全角标点。
- 代码块内的 YAML、JSON、TOML、INI 注释同样遵守以上规则。
- 书名号《》与直角引号「」只允许出现在 Markdown 文档正文中; 代码注释与 docstring 中禁用, 改用半角引号。适用范围: 本条只管代码注释与 docstring, 不管规范文档、设计文档与说明文档的正文。
- 不使用中文破折号与中文省略号; 需要停顿用半角冒号或逗号, 需要省略写具体内容。
- 违反以上任一条即交付不合格, 退回重做, 不计入完成。

### 8.2 可执行判据

违规字符清单:

| 类别 | 半角(允许) | 全角(违规) |
| --- | --- | --- |
| 逗号 | `,` | `，` |
| 冒号 | `:` | `：` |
| 分号 | `;` | `；` |
| 括号 | `(` `)` | `（` `）` |
| 引号 | `"` `'` | `“”` `‘’` |
| 句号 | `.` | `。` |
| 空格 | `U+0020` | `U+3000` |
| 连接号 | `-` | `－` `～` |
| 感叹号与问号 | `!` `?` | `！` `？` |

- 逐行扫描, 不依赖人工审查: 按字符码点匹配上表清单, 在提交前与门禁中自动执行。
- 扫描范围: 源码、脚本、构建配置、注释与 docstring; 不含二进制、生成产物与第三方源码。
- 字符串字面量内部不检查: 按语法边界识别单行与多行字符串后跳过, 不做字符判定。
- 确需全角时须在同一条注释内标注豁免理由, 形式为 `豁免: 站点文案原样保留`; 无标注即判违规。
- 扫描结果按文件、行号、字符类别输出; 同一行命中多条规则时全部列出。

### 8.3 存量处理口径

- 存量违规只记基线: 首次扫描结果按文件、行号、字符类别登记存档, 作为后续比较基线。
- 只许降不许升: 门禁比较基线与当前值, 任一类别数量升高即不通过。
- 新增违规必须为 0: 新增文件与新增改动行不允许出现违规字符。
- 禁止为变绿批量修改既有注释: 不得用脚本批量替换既有注释标点来压低基线; 存量按批次治理, 每批单独提交, 并复核替换后语义未变。
- 基线调整须说明原因与影响范围, 不得静默重设。

## 9. 裁量归属

- 某条注释是否必要存在争议时, 由该语言专家裁定, 其他人不得重复争论。
- 裁定结果写入对应语言细则的行尾注释判据一节, 以案例形式沉淀: 情形 + 结论(必写或免写) + 理由。
- 裁定仅对该语言生效, 不得跨语言套用; 跨语言共性争议提交总则修订。
- 修订生效前按现行条款执行; 已裁定案例与总则冲突时, 先按总则执行, 再由语言专家提交总则修订申请。
- 同一争议第二次出现时, 必须引用已有裁定或已登记修订, 不允许重新讨论。

## 10. 八语言对照表

| 语言 | 文件头写法 | 函数与类型注释写法 | 分区标记写法 |
| --- | --- | --- | --- |
| Python | `# ====` 上下边框, 栏间 `# ----`, 单栏 `# 文件        : name.py` | docstring 类注释写定位、工作流程、实例属性、构造参数; 函数用 `:param:` 与 `:type:` 成对, 依次 `:return:` / `:rtype:` / `:raises:` | `# =========** 名称 =========**` |
| Rust | `//!` 模块文档, 八栏逐行 | `///` 文档注释, 固定小节 `# Arguments` / `# Returns` / `# Errors` / `# Panics`; `unsafe` 必须有 `# Safety`; crate 根必须写 crate 级 lint 说明 | `// =========** 名称 =========**` |
| C | `/* */` banner, `@file` 与 `@brief` 起头 | Doxygen `@file` / `@brief` / `@param` / `@return`, 另用 `@note` 写明谁分配谁释放 | `/* =========** 名称 =========** */` |
| C++ | `/* */` banner, 同 C | 同 C, 另加类注释(类职责、成员、生命周期)与模板注释 `@tparam`; 边界函数写 `noexcept` 与错误码含义 | `/* =========** 名称 =========** */` |
| Go | 包注释 `// Package xxx ...` 紧贴 `package`, 其余文件写 `//` 八栏块 | `//` 注释, 首词为标识符名; 返回 error 必须写明何种情况返回何种错误 | `// =========** 名称 =========**` |
| Dart | `///` 八栏, 库入口置于 `library;` 之上 | `///` 文档注释, 参数以方括号引用, 例 `[name]`; 公开 API 必须注释 | `// =========** 名称 =========**` |
| TypeScript | `/** */` JSDoc 八栏, 位于 import 之前 | JSDoc `@param` / `@returns` / `@throws`; 禁止 `any` 兜底 | `// =========** 名称 =========**` |
| Shell | shebang 后 `#` 注释块, 写用途、输入、退出码、依赖命令 | 函数上方 `#` 注释写用途、参数、返回值与副作用、退出码 | `# =========** 名称 =========**` |

## 11. 违反处理

- 不符合本总则或对应语言细则的代码视为交付不合格, 退回重做, 不计入完成。
- 退回必须给出具体条款编号与位置(文件、行号), 不允许以「风格不符」笼统退回。
- 同一文件因同类问题退回两次以上, 由该语言专家补充案例到细则, 避免重复退回。
- 不得以时间紧、先合后补、后续统一清理为由豁免; 门禁不通过不得合入。
- 本总则与语言细则均不因「历史代码也这样」而放宽; 存量问题按批次治理, 新增代码按本规范执行。

## 12. 配套细则

以下三份文件与语言细则同时生效, 覆盖跨语言的通用要求, 各语言细则不得与其冲突:

| 序号 | 文件 | 适用范围 | 效力 |
| --- | --- | --- | --- |
| 09 | 09_异常捕获.md | 全语言: 异常捕获、转换、原因链、重试、敏感信息与用户可见失败文案 | 违反即交付不合格 |
| 10 | 10_日志.md | 全语言: 日志格式、字段、级别、脱敏、检索与降级 | 违反即交付不合格 |
| 11 | 11_Debug.md | 全语言: 日志开关、dry-run、调试残留、复现材料、排查沉淀与门禁纪律 | 违反即交付不合格 |

- 配套细则与总则冲突时, 以总则为准; 配套细则之间冲突时, 按更严格条款执行。

- 配套细则的修订由对应语言的专家提出, 跨语言共性条款的修订提交总则修订申请。
