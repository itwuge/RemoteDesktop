# 项目设计书（空白模板）

> **填写规则：本模板所有字段均为必填，空着即不合格，整份退回重填。**
>
> 1. 本设计书由 M03 架构师主笔，语言线会签，M01 编排拍板；未拍板通过不得据此派发任务卡。
> 2. 每个模块必须落到唯一主责岗位编号（如 P01 Rust、P06 Dart/Flutter），不得写「相关岗位」「共同负责」。
> 3. 每个接口必须写出可指认的完整签名；接口形状按 规范\14_交互契约.md 执行，桌面软件按命令函数约定，Web 项目按 HTTP API 约定，不得自创结构。
> 4. 技术选型必须同时写理由与被否决方案；涉及花钱或占用资源的，须标注「需按四类升级处理」并写明命中哪一类。
> 5. 表格不得留空单元格；确无内容时在对应单元格写结论句（如「本项目无数据模型」），不得整表留空。
> 6. 「十、通过判据」所列四项须同时满足，缺任一项即退回 M03 重写，不得派单。

## 一、基本信息

| 字段 | 填写要求 | 填写内容 |
|---|---|---|
| 项目名 | 与项目记忆一致，不得用代号或简称代替 | |
| 设计书版本 | 按 v1、v2 递增，与契约版本分别编号 | |
| 依据的需求条目编号 | 逐条列出；一份设计书可覆盖多条，不得写「见需求文档」 | |
| 主笔 | M03 架构师岗位编号 + 姓名/代号 | |
| 会签岗位 | 逐一列出参与实现的岗位编号，以语言线为主；不得只写「全体」 | |
| 拍板人 | M01 编排岗位编号 + 姓名/代号 | |
| 日期 | 年-月-日，与拍板日期一致 | |

## 二、目标与边界

| 项目 | 填写要求 | 填写内容 |
|---|---|---|
| 要解决什么 | 逐条写可观察的结果，与需求条目的「期望结果」一致，不写做法 | |
| 明确不做什么 | 逐条列出排除项，每条写明理由，与需求条目的「不包含什么」逐条一致 | |
| 本次覆盖的模块与批次 | 写明本设计书覆盖哪些模块、到哪一批为止；超出部分另开设计书 | |

> 确无排除项时写「本设计书无明确不做项」，不得留空。

## 三、架构与目录

| 项目 | 填写要求 | 填写内容 |
|---|---|---|
| 分层 | 逐层写清职责与边界，层名与目录名一致 | |
| 依赖方向 | 逐一写明允许的依赖方向（A → B）与禁止的反向依赖（B → A） | |
| 外部依赖清单 | 名称、版本、用途、许可证，以及是否花钱或占用资源 | |

目录树（按实际项目填写，不得留空）：

```text
项目根/
├─ <模块目录>/             <所属层与职责>
├─ <模块目录>/             <所属层与职责>
└─ <构建或产物目录>/       <构建产物落点>
```

## 十、通过判据

| 序号 | 判据 | 合格标准 | 不合格处理 |
|---|---|---|---|
| 1 | 每个模块有主责岗 | 模块清单每一行的主责岗位均为具体岗位编号，且唯一 | 退回 M03 重写，不得派单 |
| 2 | 每个接口有签名 | 内部接口与对外 API 每一行都有完整签名或完整路径与字段 | 退回 M03 重写，不得派单 |
| 3 | 每个里程碑有可验收产物 | 批次与里程碑每一行都有路径级产物、验收人与验收判据 | 退回 M03 重写，不得派单 |
| 4 | 技术选型有理由与被否决方案 | 技术栈每一行都写理由与被否决方案，涉及花钱或占用资源的已标注升级类别 | 退回 M03 重写，不得派单 |

> 以上四项须同时满足；缺任一项即退回 M03 重写，不得派单。
