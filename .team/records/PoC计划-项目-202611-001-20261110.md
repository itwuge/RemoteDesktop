# PoC 计划 v1.2（第 0 批）

> 依据：项目设计书 v1.1（2026-11-10）。主笔 M03 架构师，会签 P04 Python、P02 C、P01 Rust、O01 运维、T01 验收测试、S01 安全审查，M01 编排拍板。
>
> v1.1 变更（2026-11-10，M01 代裁）：4K60 升为第 0 批唯一硬指标；1080p30 只作当前无硬编硬件的条件通过基线；中继只测 L0 降级档，不承载 4K60。
>
> v1.2 变更（2026-11-10，用户拍板后 M01 代裁）：4K60 为基准且必须自动降级，1080p30 为地板；档位与阈值以设计书 3.10.1 为准；零采购，4K60 硬编与 240fps 取证标「硬件受限未验证」；Ubuntu 控制端改用 VMware 虚拟机，数据标「虚拟机口径，需真机复测」；Android 只做控制端，首个验证目标为 ARM 模拟器，数据标「ARM 模拟器口径，性能不作基线」。
>
> 本计划只覆盖第 0 批 PoC，不覆盖中继正式部署、macOS、Android 与正式发布。目标是先把一条真实链路跑通并拿到可复现的 4K60 延迟与画质证据，做到能开工。

## 一、PoC 目标与边界

| 项目 | 内容 |
|---|---|
| 一句话目标 | 打通 Windows 被控端到 Linux 控制端的局域网直连链路，在 4K60 下验证采集、编码、传输、解码、渲染、输入回传与端到端延迟指标 |
| 要验证的假设 | 1. Python 编排加硬件编码加 UDP 直连可以做到 4K60 下延迟中位数不大于 65ms、第 95 百分位不大于 110ms；2. 端到端加密不会把延迟推过上限；3. 输入回传可用；4. 同一套命令函数与消息包络可以承载后续批次，不需要推倒重来 |
| 不做什么 | 不做中继正式部署（只做 L0 降级档验证）、不做公网 NAT 穿透、不做 macOS 与 Android 正式端、不做 SPAKE2 正式鉴权、不做文件传输、不做多屏、不在中继承载 4K60、不做安装包正式签名与公证 |
| 硬件前提 | 被控端必须同时具备硬件编码器与 3840×2160 输出，4K60 才可判定为「已验证」；缺任一项只能记条件通过并保留 1080p30 基线，不得记 4K60 通过 |
| 进入下一批的条件 | 本计划第十节的通过判据全部满足，或条件通过且优化任务已排入第 1 批 |

## 二、拓扑与环境

| 角色 | 设备与系统 | 职责 | 最低要求 |
|---|---|---|---|
| 被控端 | Windows 11 22H2 及以上，有线千兆网卡，3840×2160 显示器 | 采集屏幕、编码、发送码流、注入输入 | 支持 DXGI Desktop Duplication；至少一种硬件编码器（NVENC、QSV、AMF）；4K60 输出 |
| 控制端 | Ubuntu 22.04 LTS，Xorg 会话，有线千兆网卡，3840×2160 显示器 | 接收码流、解码、渲染、采集输入并回传 | Python 3.12；OpenGL 3.3 及以上；可运行 PySide6；具备硬件解码器与 4K60 输出 |
| 信令 | 控制端本机进程，监听回环与局域网地址 | 设备注册、挑战应答、offer/answer/candidate 转发 | 只用于 PoC，不依赖现有 ECS |
| 取证 | 240fps 手机或高速摄像机，三脚架 | 同框拍摄两端屏幕，逐帧计算输入到画面延迟 | 可导出逐帧时间戳 |
| 网络 | 同一千兆交换机，不跨 VLAN | 先测局域网基线，不做损伤 | 有线连接，禁用 Wi-Fi |

环境约束：

- 构建、虚拟环境、录像与 CSV 一律写入 `%RDC_BUILD_ROOT%`，不得落系统盘；开工前由 O01 实测可用空间并记录。
- 两台机器启用 NTP，时钟偏差不大于 50ms；端到端延迟以摄像机逐帧为准，不以两台机器时钟差为准。
- 关闭 Windows 全屏独占程序、Linux 桌面特效与自动更新，避免干扰采样。
- PoC 代码只放 `poc/`，不进入 `src/rdc/` 发布路径；PoC 依赖不进入发布锁文件。

## 三、技术路径

| 环节 | PoC 采用 | 与正式方案的关系 | 许可证备注 |
|---|---|---|---|
| 采集 | Windows 用 dxcam 取 DXGI 帧，带单调时钟时间戳 | 正式版替换为 P02 的 C 模块，接口不变 | dxcam 为 PoC 专用，许可证以锁定版本为准，S01 复核 |
| 色彩转换 | NumPy 转 NV12 或 I420 | 正式版放 C 模块或 FFmpeg 滤镜 | NumPy BSD-3-Clause |
| 编码 | PyAV 调用 FFmpeg，优先 `h264_nvenc`、`h264_qsv`、`h264_amf`；4K60 必须硬件编码，软件编码只允许在 1080p30 基线下使用 | 正式版走 P02 的 FFmpeg C ABI 桥；硬件编码器缺失时 4K60 直接判为未验证 | PyAV BSD-3-Clause；随包 FFmpeg 构建参数由 S01 复核，禁止 GPL 组件进入发布 |
| 传输 | asyncio UDP 直连，三向握手，ChaCha20-Poly1305 加密，测试用预共享密钥 | 正式版换成设备签名与 SPAKE2 派生会话密钥，传输骨架不变 | cryptography Apache-2.0 或 BSD-3-Clause |
| 信令 | 本机 WSS 加 JSON，包络与消息类型按设计书 5.3 | 正式版接 ECS 信令服务，消息不变 | 无新增依赖 |
| 解码 | PyAV 解码 H.264 | 正式版走 P02 的 FFmpeg C ABI 桥 | 同上 |
| 渲染 | PySide6 QOpenGLWidget 上传纹理渲染 | 正式版保留 Qt RHI 或 OpenGL 路径，Android 换 SurfaceView | PySide6 LGPL-3.0 |
| 输入 | Linux 捕获鼠标与键盘事件，经加密通道回传，Windows 用 SendInput 注入 | 正式版输入适配层不变 | 无新增依赖 |
| 指标 | 管线时间戳 CSV 加 240fps 摄像机逐帧 | 正式版由 T01 沿用同一取证口径 | 无新增依赖 |
| 打包 | 第 0 批只做可运行目录与启动脚本，不做正式安装包 | 第 1 批再上 Nuitka 与安装包 | 无新增依赖 |

## 五、指标与测量方法

| 指标 | 4K60 直连目标（唯一硬指标） | 1080p30 软件基线（仅当前硬件缺失时用于条件通过） | 测量方法 | 采样量 | 证据 |
|---|---|---|---|---|---|
| 端到端输入到画面延迟 | p50 不大于 65ms，p95 不大于 110ms | p50 不大于 80ms，p95 不大于 120ms | 被控端显示毫秒计时器；控制端渲染同一画面；240fps 摄像机同框拍摄；逐帧数出点击到画面变化 | 30 次点击，至少 5 分钟会话 | 逐帧 CSV、录像原文件 |
| 渲染帧率 | 不低于 57fps；单帧间隔超过 100ms 的次数为 0 | 不低于 28fps；单帧间隔超过 200ms 的次数为 0 | 控制端渲染回调记录单调时间戳 | 连续 5 分钟 | 渲染日志 |
| 画质 | 静态文档 SSIM 不小于 0.97；10pt 中文字符可辨认 | SSIM 不小于 0.95 | 控制端截图与被控端原图用 FFmpeg 计算 SSIM；T01 与 U01 双人盲评 | 3 张静态文档、2 段滚动窗口 | 截图、SSIM 输出、盲评记录 |
| 采集耗时 | p50 不大于 6ms，p95 不大于 8ms | 单帧不大于 8ms | 采集回调前后单调时间戳 | 连续 5 分钟 | 管线 CSV |
| 编码耗时 | 硬件编码 p50 不大于 8ms，p95 不大于 15ms | 软件编码不大于 30ms | 编码前后单调时间戳，按编码器分组 | 连续 5 分钟 | 管线 CSV |
| 解码耗时 | 硬件解码 p50 不大于 6ms，p95 不大于 10ms | 单帧不大于 10ms | 解码前后单调时间戳 | 连续 5 分钟 | 管线 CSV |
| 渲染耗时 | 单帧不大于 8ms | 单帧不大于 8ms | 渲染前后单调时间戳 | 连续 5 分钟 | 管线 CSV |
| GPU 与 CPU | GPU 不超过 70%（编码、解码各不超过 20%）；8 核 CPU 不超过 25% | 4 核机器采集加编码不超过 80% | Windows GPU Engine 计数器加 psutil 按秒采样 | 连续 5 分钟 | GPU 与 CPU CSV |
| 码率 | 16 至 40Mbps，默认 25Mbps | 3 至 6Mbps | ffprobe 校验码流；发送端统计字节 | 连续 5 分钟 | ffprobe 输出、发送统计 |
| 建连时延 | 第 95 百分位不大于 3 秒 | 同 4K60 口径 | 点击连接到首帧显示计时 | 30 次 | 建连 CSV |
| 长时稳定 | 连续 60 分钟无崩溃、无断流；内存增长不大于 10% | 连续 30 分钟，内存增长不大于 10% | 进程 RSS 首尾对比；会话日志 | 60 分钟 | RSS 采样、会话日志 |
| 加密开销 | 开启 AEAD 后延迟增加不超过 5ms | 同 4K60 口径 | 同一链路分别测明文与密文，比较中位数 | 各 30 次 | 对比 CSV |

测量口径：

- 全项目只有这一套指标，按档位判定。4K60 是基准档，必须带自动降级；1080p30 是地板，自动逻辑不得低于该档；中继按 L0 至 L3 单独判定，不套用直连档位表。
- 4K60 判定必须同时满足硬件编码器与 3840×2160 输出；缺任一项，报告只能写「4K60 硬件受限未验证」，不得用 1080p30 数据冒充，也不得写成通过。
- 1080p30 地板必须实测：P0-03 已完成 1080p30 软编实测（8915 帧、29.71fps、采集 p50 5.541ms、编码 p50 11.67ms、CPU 184.23%），证据见 `%RDC_BUILD_ROOT%\evidence\poc\csv\p0-03_summary.json`；硬编口径待复测。
- 端到端延迟以摄像机逐帧为准；无 240fps 设备时如实写「替代口径不可得」，管线时间戳只用于定位瓶颈，不用于对外宣称。
- 虚拟机、模拟器、软编三种口径的数据必须在报告中逐条标注，不得写成真机或硬编结论。
- 每次测量记录编码器、分辨率、帧率、码率、系统版本、GPU 型号与驱动版本。
- 任何一次测量出现丢帧、黑屏、断流，整组样本作废重测，不作废记录必须写明原因。
- 指标只报实测值，不报估算值；报告里每个数字都能指认到原始 CSV 或录像。

## 六、失败判据与放行规则

| 级别 | 判据 | 处理 |
|---|---|---|
| 红线失败 | 30 次建连中连续 3 次无法在 3 秒内建立直连；或会话 10 分钟内崩溃、断流；或输入完全不可用；或中继之外出现明文媒体 | 停止 PoC，M03 重评架构，M01 重排；不得进入第 1 批 |
| 4K60 指标失败 | 具备硬编与 4K 输出时：p50 大于 75ms，或 p95 大于 130ms；或帧率低于 55fps；或 SSIM 小于 0.95；或 GPU 持续高于 80% | 允许两轮优化；两轮后仍不达标，按失败处理 |
| 4K60 条件通过 | p50 65 至 75ms，或 p95 110 至 130ms，或帧率 55 至 57fps | 可进入第 1 批，但必须带性能优化任务卡，优化未完成不得进 beta |
| 硬件不满足（当前实况） | 无可用硬件编码器，或显示器低于 3840×2160 | 记条件通过：只认 1080p30 基线，结论写明「4K60 未验证」并列出补测硬件清单；不得记为 4K60 通过 |
| 1080p30 基线失败 | p50 大于 100ms，或 p95 大于 150ms；或帧率低于 25fps；或 SSIM 小于 0.90；或 CPU 持续高于 80% | 允许两轮优化；两轮后仍不达标，按失败处理 |
| 通过 | 第五节 4K60 全部指标达标，且无红线失败 | 进入第 1 批 |

优化顺序固定为：硬件编码是否真正启用 → 零拷贝与色彩转换 → 渲染上传方式 → 传输批处理与抖动缓冲 → 原生传输热路径。每轮优化只改一个变量，改完重测同一组样本。
