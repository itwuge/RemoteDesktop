## 一、结论摘要

| 平台 | 采集技术最好的是谁 | 好在哪 | 我们的取舍 |
|---|---|---|---|
| Windows | 全屏低延迟：Sunshine 的 DXGI Desktop Duplication 路径；工程完整度：RustDesk；窗口级：OBS 的 Windows.Graphics.Capture | DXGI 直接拿桌面纹理，脏区与移动矩形增量最小，配合 NVENC 可做到采集加编码 10ms 级；WGC 能按窗口/应用采集且由系统处理遮挡与缩放 | 全屏走 DXGI Desktop Duplication（`DuplicateOutput1` 优先，`DuplicateOutput` 回退，GDI 兜底）；窗口级留 WGC 作为后续能力，不在首版实现 |
| macOS | OBS 的 ScreenCaptureKit 实现；RustDesk 仍在用已弃用的 CGDisplayStream | SCK 是 Apple 现行唯一推荐路径，支持显示器/窗口/应用三级过滤、脏区、光标与 HDR，CGDisplayStream 已被标记弃用 | 直接上 ScreenCaptureKit，不沿用 CGDisplayStream；OBS 仅作迁移参照 |
| Linux | X11 低延迟：TigerVNC 的 XShm + XDamage 工程划分最规范；Wayland 通用：RustDesk 与 OBS 的 PipeWire/portal；极限低延迟：Sunshine 的 KMS/NvFBC | XShm 零拷贝共享内存加脏区事件，X11 下开销最小；PipeWire 是 Wayland 唯一通用授权路径；NvFBC 绕开合成器但绑定 NVIDIA 与 X11 | 主路径 X11 XShm + XDamage；Wayland 走 PipeWire/portal 并明示限制；NvFBC 不作默认，只作可选加速 |
| Android | scrcpy | MediaProjection + VirtualDisplay + MediaCodec Surface 零拷贝，采集即编码，不落 CPU 内存；输入走 UHID/AOA 低延迟 | 产品化只走 MediaProjection；SurfaceControl 路径依赖 shell 权限，不采用 |

一句话结论：**没有单一项目在四端都做到最好。** Windows 看 Sunshine 与 RustDesk，macOS 看 OBS，Linux 看 TigerVNC 与 Sunshine，Android 看 scrcpy。本项目按平台各取所长，协议与业务层自研，不引入任何上游代码。

## 二、横评方法与口径

三条评价线：

- 功能：能否采集、编码、传输、解码、渲染、注入输入、传文件、传音频、多屏、剪贴板；延迟与画质档位。
- 界面：是否面向终端用户、是否有设备码/口令、是否展示通路与画质、是否可无人值守。
- 受众：个人远程办公、IT 运维、游戏串流、开发者调试、容器化桌面。

采集逐平台拆开比，不按「项目整体」打分：

| 平台 | 候选技术 | 判定维度 |
|---|---|---|
| Windows | DXGI Desktop Duplication、Windows.Graphics.Capture（WGC） | 帧获取路径、脏区/移动矩形、光标、遮挡处理、权限、多 GPU、全屏独占程序兼容 |
| macOS | ScreenCaptureKit（SCK）、CGDisplayStream | 是否弃用、权限模型、过滤粒度、脏区、HDR、系统版本下限 |
| Linux | PipeWire/portal、X11 SHM（XShm）、NvFBC、KMS/DRM | Wayland 可用性、授权模型、零拷贝、延迟、硬件绑定 |
| Android | MediaProjection + VirtualDisplay、MediaProjection + SurfaceControl、MediaCodec Surface | 权限、是否零拷贝、是否需 shell、Android 版本下限、输入通道 |

证据等级：A 官方发布页或变更日志；B 仓库源码路径或提交；C 公开文档或第三方整理。本文结论至少有一条 A 或 B 支撑。

## 三、项目逐项横评

### 3.1 RustDesk

| 项目 | 内容 |
|---|---|
| 版本与日期 | 1.5.1（2026-11-01），1.5.0（2026-09-30） |
| 许可证 | AGPL-3.0 |
| 来源 | https://github.com/rustdesk/rustdesk ；https://rustdesk.com/blog/rustdesk-1-5-0-webrtc-qos/ ；https://releasealert.dev/github/rustdesk/rustdesk |

功能：自建中继（hbbs/hbbr）、设备码加临时口令、文件传输、剪贴板、多屏、部分平台音频、1.5.0 起加入 WebRTC 直连路径与 HDR 色调映射。采集实现：

| 平台 | 实现 | 证据 |
|---|---|---|
| Windows | DXGI Desktop Duplication，`DuplicateOutput1` 优先，失败回退 `DuplicateOutput`，再失败用 GDI；处理脏区、移动矩形与光标 | 仓库 `libs/scrap/src/windows/`（B，本次未逐行复核） |
| macOS | CGDisplayStream（已被 Apple 弃用） | 仓库 `libs/scrap/src/darwin/`（B，未复核）；Apple 弃用状态为 C |
| Linux | X11 XShm；Wayland 走 PipeWire/portal | 仓库 `libs/scrap/src/linux/`（B，未复核） |
| Android | MediaProjection + VirtualDisplay | 仓库 `libs/scrap/src/android/`（B，未复核） |

界面：面向个人与小型 IT，单窗口、设备码加口令，通路与画质信息展示有限。

受众：个人远程办公、自建服务器用户、受商业远控价格影响的团队。

结论：**Windows 采集的行为参照首选**；macOS 采集路径已落后，不作参照。

### 3.2 Sunshine + Moonlight

| 项目 | 内容 |
|---|---|
| 版本与日期 | Sunshine 稳定版 v2026.914.233613（2026-09-14），beta v2026.817.185037；Moonlight v6.2.0（2026-10-04） |
| 许可证 | Sunshine GPL-3.0；Moonlight GPL-3.0 |
| 来源 | https://github.com/LizardByte/Sunshine ；https://docs.lizardbyte.dev/projects/sunshine/master/md_docs_2changelog.html ；https://github.com/moonlight-stream/moonlight-qt |

功能：游戏串流为主，硬件编码优先（NVENC/QSV/AMF/VAAPI/VideoToolbox），零延迟调优、无 B 帧、动态码率、HDR、手柄与输入。采集实现：

| 平台 | 实现 | 证据 |
|---|---|---|
| Windows | 默认 DXGI Desktop Duplication（ddx）；WGC 为 beta 路径 | 仓库 `src/platform/windows/display_capture.cpp`、`display_capture_wgc.cpp`（B，未复核） |
| Linux | KMS/DRM 捕获、PipeWire/portal、NvFBC 可选 | 仓库 `src/platform/linux/`（B，未复核） |
| macOS | 基于 AVFoundation 的显示捕获路径 | 仓库 `src/platform/macos/`（B，未复核；是否已迁 SCK 未确认） |

界面：Web 管理界面加托盘，配置项多，偏极客。

受众：游戏串流、家庭云游戏、低延迟桌面串流。

结论：**编码参数取向（硬件优先、零延迟、无 B 帧、关键帧策略）直接作为本项目 3.6 的依据**；不采用其 GameStream 协议栈；Linux 的 KMS/NvFBC 只作可选加速参照。

| 许可证 | Janus GPL-3.0；mediasoup ISC；libwebrtc BSD-3-Clause |

### 3.6 scrcpy（Android 采集标杆）

| 项目 | 内容 |
|---|---|
| 版本与日期 | v5.0.1（2026-10-08） |
| 许可证 | Apache-2.0 |
| 来源 | https://github.com/Genymobile/scrcpy ；https://github.com/Genymobile/scrcpy/releases |

## 四、逐平台采集技术横评

### 4.1 Windows：DXGI Desktop Duplication vs Windows.Graphics.Capture

| 维度 | DXGI Desktop Duplication | Windows.Graphics.Capture（WGC） |
|---|---|---|
| 系统版本 | Windows 8 起 | Windows 10 1803 起，1903 后稳定 |
| 采集粒度 | 整屏/单显示器 | 显示器、窗口、应用 |
| 增量机制 | 脏区与移动矩形，可只取变化区域 | 系统帧池，按帧交付，脏区信息有限 |
| 遮挡与最小化 | 直接取桌面输出，全屏独占程序可能失败 | 窗口被遮挡仍可采（系统合成），最小化通常停帧 |
| 光标 | 可单独取光标元数据，便于本地合成 | 可包含或排除光标 |
| 权限 | 无额外授权弹窗 | 首次可能弹系统授权；受保护内容黑屏 |
| 延迟 | 更低，路径短，可零拷贝进编码器 | 略高，多一层系统合成与帧池调度 |
| 多 GPU | 需按输出适配器选择 | 由系统处理 |
| 代表实现 | Sunshine（ddx）、RustDesk、libwebrtc | OBS 窗口捕获、libwebrtc 窗口路径 |

判定：**全屏低延迟选 DXGI Desktop Duplication；按窗口采集选 WGC。** 首版只做全屏，因此选 DXGI，并在实现上参照 RustDesk 的回退链（`DuplicateOutput1` → `DuplicateOutput` → GDI）与 Sunshine 的编码闭环。

### 4.2 macOS：ScreenCaptureKit vs CGDisplayStream

| 维度 | ScreenCaptureKit | CGDisplayStream |
|---|---|---|
| 状态 | Apple 现行推荐，macOS 12.3 起 | 已被 Apple 标记弃用 |
| 粒度 | 显示器、窗口、应用 | 仅显示器 |
| 权限 | 屏幕录制授权（TCC），首次弹窗 | 同样需屏幕录制授权 |
| 增量 | 支持脏区、帧状态、光标开关 | 支持帧回调，增量能力弱 |
| HDR/色彩 | 支持 HDR 与色彩空间信息 | 支持有限 |
| 代表实现 | OBS 29+、新版 libwebrtc | RustDesk（仍在用） |

判定：**只有一个正确答案：ScreenCaptureKit。** CGDisplayStream 已弃用，且无法按窗口采集，不作为新项目路径。

### 4.3 Linux：PipeWire/portal vs X11 SHM vs NvFBC vs KMS/DRM

| 维度 | PipeWire + portal | X11 SHM（XShm/XDamage） | NvFBC | KMS/DRM |
|---|---|---|---|---|
| 会话 | Wayland 与 X11 均可（portal 授权） | 仅 X11 | 仅 X11 + NVIDIA | 无合成器或独占场景 |
| 授权 | 系统门户弹窗，用户选择屏幕/窗口 | 直接读 X 显示，无需弹窗 | 需 NVIDIA 驱动与补丁接口 | 需 DRM 主设备权限 |
| 延迟 | 中，多一层 portal 与 PipeWire 缓冲 | 低，共享内存零拷贝 | 最低，绕开合成器 | 低，但需接管显示 |
| 兼容性 | Wayland 唯一通用路径 | 存量 X11 最广 | 绑定 NVIDIA 与版本 | 绑定具体硬件与场景 |
| 代表实现 | RustDesk、OBS、libwebrtc | TigerVNC、x11vnc、RustDesk | Sunshine 可选 | Sunshine、Wolf |

判定：**主路径 X11 XShm + XDamage；Wayland 必须走 PipeWire/portal 并明示限制；NvFBC 与 KMS 只作可选加速，不作默认。**

### 4.4 Android：MediaProjection + VirtualDisplay / SurfaceControl

| 维度 | MediaProjection + VirtualDisplay | MediaProjection + SurfaceControl | MediaCodec Surface 编码 |
|---|---|---|---|
| 权限 | 运行时用户授权，普通应用可用 | 需 shell/系统权限，普通应用不可用 | 无额外权限 |
| 版本 | Android 5 起 | Android 14 起（受限） | Android 5 起 |
| 零拷贝 | 可把 VirtualDisplay 直接输出到编码器 Surface | 可进一步跳过虚拟显示合成 | 编码器 input surface，避免 CPU 拷贝 |
| 延迟 | 低 | 更低 | 采集到编码零拷贝的关键 |
| 代表实现 | scrcpy（默认路径） | scrcpy（Android 14+ 且具备 shell） | scrcpy、MediaCodec |

判定：**产品化只走 MediaProjection + VirtualDisplay + MediaCodec Surface 零拷贝**；SurfaceControl 依赖 shell 权限，不进入普通 APK。

## 五、四平台横向总表

| 平台 | 最优采集 | 次优 | 不选 | 首版是否实现 |
|---|---|---|---|---|
| Windows | DXGI Desktop Duplication | WGC（窗口级） | GDI 轮询（仅兜底） | 是，DXGI |

| x11vnc / TigerVNC | 中：RFB，画质与延迟有限 | 低到中：命令行或轻量客户端 | Linux 运维 | Linux X11 结构参照 |
| Janus / mediasoup / libwebrtc | 高：SFU 与浏览器生态 | 无终端界面 | 平台方与开发者 | 只取平台采集结论，不引入栈 |
| OBS | 高：源与滤镜最全 | 高但学习成本高 | 主播与录屏 | 窗口采集与 macOS SCK 参照 |
| scrcpy | 高：Android 镜像与控制 | 中：命令行加轻量窗口 | 开发者 | Android 采集标杆 |

## 七、选型结论与理由

1. **Windows 采集**：DXGI Desktop Duplication，`DuplicateOutput1` 优先、`DuplicateOutput` 回退、GDI 兜底；按输出适配器选择，处理旋转与多 GPU；光标元数据单独取，渲染端合成。理由：全屏场景延迟最低，且 Sunshine 与 RustDesk 两条独立实现都验证了该路径。
2. **macOS 采集**：ScreenCaptureKit，不做 CGDisplayStream 兼容层。理由：Apple 已弃用后者，新项目没有理由背技术债。
3. **Linux 采集**：X11 走 XShm + XDamage，参照 TigerVNC 的模块划分；Wayland 走 PipeWire/portal，明确提示用户授权；NvFBC 与 KMS 只作为可选加速，默认关闭。理由：兼容性与延迟的最优折中，且不把发行版与驱动差异带进主路径。
4. **Android 采集**：只做控制端，不采集；若后续做被控，走 MediaProjection + VirtualDisplay + MediaCodec Surface。理由：普通 APK 只有这一条合法且低延迟的路径。
5. **编码与协议**：硬件编码优先、零延迟、无 B 帧、2 秒关键帧、丢包即请求 IDR，取向参照 Sunshine；协议自研，不采用 GameStream、RFB 或完整 WebRTC。
6. **不引入上游代码**：RustDesk 与 Sunshine 为 AGPL/GPL，OBS、x11vnc、TigerVNC、Looking Glass 为 GPL，Janus 为 GPL；只有 scrcpy（Apache-2.0）、mediasoup（ISC）、libwebrtc（BSD-3-Clause）、Wolf（MIT）、Selkies（MPL-2.0）、Guacamole（Apache-2.0）在许可证上可复用，但本项目仍选择不复制，只借结论，避免维护与许可证双重负担。
7. **复用边界**：协议、信令、会话、加密、画质策略、命令契约、指标日志完全复用；采集、硬编硬解、输入注入、渲染 surface、权限必须原生。详见设计书 3.13。
