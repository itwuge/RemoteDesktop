## 三、架构与目录

### 3.1 分层

| 层 | 职责 | 边界 | 目录 |
|---|---|---|---|
| 界面层 | 收集参数、调用一个命令函数、呈现结果 | 不写业务判断，不直接读写文件与网络，不改写 `message` | `src/rdc/ui/`、`android/` |
| 命令层 | 一个用户动作一个命令函数，统一返回 `CommandResult` | 不弹窗、不阻塞界面线程、不打印用户提示 | `src/rdc/commands/` |
| 会话编排层 | 会话状态机、连接阶段、画质控制、指标汇总 | 只依赖端口，不直接构造具体实现 | `src/rdc/session/` |
| 能力层 | 信令、传输、媒体、输入、加密 | 通过端口暴露能力，不反向依赖界面与命令层 | `src/rdc/signaling/`、`src/rdc/transport/`、`src/rdc/media/`、`src/rdc/input/`、`src/rdc/crypto/` |
| 端口与适配层 | 端口定义、平台适配、原生桥 | 具体实现只在装配处选择；原生模块只经 C ABI 进入 | `src/rdc/contracts/`、`src/rdc/platform/`、`native/` |
| 中继服务 | 信令会合、令牌校验、密文转发、预算与准入 | 不导入界面、媒体与客户端会话代码；只看密文与元数据 | `src/rdc/relay/` |
| 基础设施层 | 配置、标识、错误、结果结构、日志 | 不依赖任何上层 | `src/rdc/core/` |

### 3.2 依赖方向

允许的依赖方向：

- 界面层 → 命令层 → 会话编排层 → 端口定义。
- 平台适配、媒体适配、传输适配、输入适配 → 端口定义；由装配处注入会话编排层。
- 原生桥 → 平台适配；原生桥只暴露 C ABI，不把平台对象泄漏到 Python 层。
- 中继服务 → 协议与加密端口；中继不依赖媒体、界面与客户端会话。
- 测试与工具 → 全部模块，只读调用，不反向被业务代码依赖。

禁止的反向依赖：

- `core` 不得导入 `ui`、`commands`、`media`、`transport`。
- `ui` 不得导入 `media`、`transport`、`crypto` 的具体实现，只能经命令层。
- `media` 不得导入 `ui`；`transport` 不得导入 `session`；`relay` 不得导入 `media` 与 `ui`。
- 命令层不得直接构造数据库、网络客户端、采集器、编码器；一律由装配处注入。
- 平台适配层不得把 Windows、macOS、Linux、Android 的对象类型暴露给会话层。

### 3.6 编码管线

数据流固定为：采集帧 → 时间戳 → 色彩转换（NV12/I420） → 硬件编码优先 → 打包 → AEAD 加密 → 传输 → 抖动缓冲 → 解码 → 渲染。

- 编码器选择顺序：Windows 依次尝试 NVENC、QSV、AMF；macOS 用 VideoToolbox；Linux 依次尝试 VAAPI、NVENC；Android 用 MediaCodec。全部不可用时用 OpenH264 软件编码兜底。
- 编码参数：H.264，4:2:0，8 位，无 B 帧，零延迟调优，关键帧间隔 2 秒或丢包后立即请求 IDR，开启帧内刷新以降低丢包扩散。
- **4K60 硬性前提：直连档必须使用硬件编码器。** 软件编码只用于 1080p30 及以下兜底，不承诺 4K60。依据：第 0 批实测 libx264 ultrafast 在 1080p30 下 CPU 平均 184%（20 线程机器约 1.84 核），按像素率 8 倍推算 4K60 需约 14.7 核，普通 8 核机器不可行；证据 `%RDC_BUILD_ROOT%\evidence\poc\csv\p0-03_summary.json`。

4K60 直连延迟预算（SDR、单屏、局域网或同城直连）：

| 阶段 | 预算 | 依据与说明 |
|---|---|---|
| 采集 | 3 至 6ms | DXGI Desktop Duplication 或 ScreenCaptureKit 单帧取回，P0-03 实测 1080p 采集 p50 5.54ms |
| 色彩转换与上传 | 1 至 3ms | NV12/I420 转换与显存拷贝，零拷贝路径可取下限 |
| 硬件编码 | 4 至 8ms | NVENC、QSV、VideoToolbox 一帧延迟，不含编码器排队 |
| 打包与 AEAD | 1 至 2ms | 分片、序号、ChaCha20-Poly1305 |
| 网络单程 | 5 至 15ms | 直连同城；同网段可低至 1 至 3ms |
| 抖动缓冲 | 8 至 17ms | 60fps 下 1 帧为 16.7ms，按反馈自适应，最低 8ms |
| 硬件解码 | 3 至 6ms | D3D11VA、VideoToolbox、VAAPI、MediaCodec |
| 渲染与合成 | 3 至 8ms | 含桌面合成与显示扫描输出 |
| 合计 | p50 28 至 65ms，p95 不大于 110ms | 由 T01 用 240fps 同框取证复核，预算为设计上限不是实测结论 |

4K60 码率区间：H.264 High 4:2:0 8bit，桌面内容默认 25Mbps，区间 16 至 40Mbps，按实测链路带宽与画面复杂度在区间内调整；静态文档可取区间下限，视频或滚动场景取上限。首版不启用 HEVC 与 AV1，避免四端硬解能力不一致。

4K60 开销预算：硬件编码占用 GPU 不超过 20%，解码不超过 20%，采集加渲染加合成合计不超过 30%，整机 GPU 不超过 70%；Python 侧打包、加密与调度在 8 核机器上不超过 2 核（25%）。超预算即触发帧率或分辨率降档，不允许静默掉帧。

- 弱网策略：以 200ms 为采样周期收集 RTT、丢包率、发送队列、解码与渲染耗时；画质控制器按 AIMD 调整码率与档位，降档立即生效，升档需连续 5 秒稳定且每次只升一档。
- 中继预算：中继模式下画质档位不得超过 `RelayPolicy` 计算出的预算。单会话预算按 `egress_mbps × 1000 × (1 - overhead_ratio) ÷ max_sessions` 计算,不得把 3 Mbps 或任何带宽值写进协议常量。以部署默认值 3 Mbps、开销比 0.08、单会话为例，预算 2760kbps，对应 720p30 档（视频 2000kbps）；把 `max_sessions` 配为 2 时预算 1380kbps，只允许降到 960×540@30 档（1200kbps）。
- 中继降级档（固定四档，分辨率与码率绑定，不允许自由组合）：L0 1280×720@30、2000kbps；L1 960×540@30、1200kbps；L2 640×360@20、600kbps；L3 仅音频级保活 200kbps（黑屏加光标）。任何中继档都不提供 4K60，界面对用户明示「中继模式已降级」。

### 3.7 P2P 打洞、降级判定与切换

候选收集：

- 本机候选：本地网卡地址与端口。
- 反射候选：经配置的 STUN 服务获取公网映射地址；STUN 地址来自配置，不写死公共服务器。
- 中继候选：由信令服务分配的中继端点与令牌。

直连流程：

1. 双方经信令交换候选与会话意图，携带设备签名与一次性随机数。
2. 双方并行向候选对发送打洞包，包内带 Cookie 与签名，防放大与伪造。
3. 收到对端响应后执行 X25519 临时密钥交换与 AEAD 密钥确认，完成三向握手。
4. 握手成功后进入直连数据面；直连尝试总时限默认 3000ms，来自配置 `direct_timeout_ms`。

降级判定（通路）：

- 候选对全部失败或直连握手超过时限，立即申请中继。
- 直连已建立但连续 5 秒 RTT 大于 300ms 或丢包率大于 10%，且中继预算可用，切到中继。
- 中继不可用时不回退到明文或未加密通道，会话失败并给出用户可见文案。
- 首版每个会话最多切换一次通路；中继升直连只在新会话尝试，避免会话中反复抖动。

画质档位判定（与通路解耦，输入只有三项：通路类型、实测带宽、硬件能力）：

| 通路 | 档位 | 进入条件 | 码率 |
|---|---|---|---|
| P2P | 4K60 | 硬件编码可用、被控端分辨率不低于 3840×2160、链路实测可用带宽不低于 60Mbps 且持续 2 秒 | 16 至 40Mbps，默认 25Mbps |
| P2P | 1440p60 | 硬件编码可用、带宽不低于 35Mbps | 10 至 20Mbps |
| P2P | 1080p60 | 硬件编码可用、带宽不低于 15Mbps | 6 至 12Mbps |
| P2P | 1080p30 | 仅有软件编码，或带宽不足 15Mbps | 3 至 6Mbps |
| 中继 | L0 至 L3 | 只由 `RelayPolicy` 预算决定，见 3.6 | 2000、1200、600、200kbps |

自动判定与切换规则：

1. 建连时先做通路判定：直连成功进入 P2P 档位判定，直连失败按中继预算选 L0 至 L3。
2. 通路内每 1 秒采样一次，使用 5 个样本的指数滑动平均；丢包大于 2%、编码队列超过 2 帧或 GPU 占用超过 85% 连续 2 个采样窗口，立即降一档。
3. 降档一次只降一档，两次降档间隔不少于 5 秒；升档要求连续 10 秒丢包小于 1%、RTT 小于 120ms、编码队列为空，且一次只升一档。
4. 4K60 只在 P2P 且带宽探针达标时尝试；带宽探针不达标即降到 1440p60，不允许「先开 4K 再看」。
5. 中继档位与 P2P 档位共用同一套控制器，不另写一套策略；中继永远不尝试 4K60，也不因用户手动请求而放开。

切换行为：

- 切换由传输路径管理器统一执行，会话层只收到 `transport_kind` 变更事件。
- 切换期间保持输入事件排队不超过 500ms，超过则丢弃并提示，不无限积压。
- 界面显示直连、中继、正在切换三种状态，状态与实际路径管理器一致；中继模式必须同时显示当前分辨率与档位，避免用户误以为仍在 4K60。

### 3.8 信令与鉴权

信令走 WSS 与 TLS 1.3，消息为 JSON，协议版本 v1。消息包络固定七字段：`v`、`type`、`id`、`session_id`、`ts`、`payload`、`sig`。

设备身份：

- 首次启动生成 Ed25519 密钥对，私钥写入系统密钥库（Windows DPAPI、macOS Keychain、Linux libsecret、Android Keystore）。
- `device_id` 取公钥 SHA-256 的 Base32 前 20 字符，作为设备唯一标识。
- 设备注册时只上传公钥与能力声明，不上传私钥与口令。

连接鉴权：

- 临时连接：被控端显示 6 位一次性口令，有效期 5 分钟，失败 5 次锁定 15 分钟。
- 固定连接：被控端保存 Argon2id 口令散列，双方用 SPAKE2 做口令认证密钥交换，口令本身不经网络传输。
- 双方在信令通道上交换 SPAKE2 消息，服务端只转发不透明数据；认证成功后各自派生会话密钥。
- 服务端对设备签名做校验，签发 5 分钟有效的会话令牌与中继令牌；令牌只放请求头或消息体，不进 URL、不进日志。

会话密钥：

- 每次会话生成临时 X25519 密钥对，经 HKDF-SHA256 派生双向密钥。
- 媒体与控制消息使用 ChaCha20-Poly1305，96 位随机起始 nonce 加单调计数器，禁止重用。
- 每 30 分钟或累计 1GB 数据触发重密钥；重密钥期间旧密钥保留一个短窗口，避免丢包。

中继令牌：

- 中继令牌绑定 `session_id`、设备标识、预算与过期时间，由信令服务签发。
- 中继只校验令牌与转发密文，不持有会话密钥，不解析媒体内容。

### 3.9 会话安全

威胁模型覆盖：被动窃听、主动中间人、恶意中继、重放、口令暴力尝试、屏幕采集未授权、日志与制品泄露。

- 传输：信令 TLS 1.3；直连数据面 AEAD；中继 TLS 1.3 加端到端 AEAD，双层保护。
- 身份：设备密钥签名挑战随机数；首次配对需被控端本地确认；设备指纹变化时提示用户重新确认。
- 授权：被控端明确展示正在被控制状态；macOS 显示屏幕录制指示；Android 控制端无被控能力。
- 防重放：消息带单调序号与时间戳，服务端维护 5 分钟窗口；重复消息丢弃并计数。
- 防爆破：一次性口令 5 分钟失效，失败 5 次锁定 15 分钟；固定口令失败按设备与来源双维度限速。
- 日志与制品：口令、令牌、私钥、会话密钥不进入日志、制品、构建摘要与仓库；日志按 10_日志 脱敏；崩溃转储默认关闭。
- 依赖与许可证：S01 在依赖引入前复核；发布前做一次会话安全评审，未签字不放行。

#### 3.10.1 直连画质档位与自动降级（v1.2 新增，对应契约 v1.1）

| 档位 | 分辨率@帧率 | 码率 默认（区间） | 链路带宽需求 | 降档触发（连续 3 秒任一满足） | 回升条件（连续 10 秒全部满足） | 每会话进入上限 |
|---|---|---|---|---|---|---|
| 4K60 | 3840×2160@60 | 25000 kbps（16000–40000） | 不低于 50000 kbps | 帧率<54；p95>110ms；丢包≥2%；GPU>70%；CPU>25%；带宽<50000 kbps | p95≤80ms；丢包<0.3%；GPU≤55%；CPU≤15%；带宽≥65000 kbps | 2 次 |
| 1440p60 | 2560×1440@60 | 14000 kbps（10000–22000） | 不低于 28000 kbps | 帧率<54；p95>100ms；丢包≥3%；GPU>70%；CPU>25%；带宽<28000 kbps | p95≤75ms；丢包<0.5%；GPU≤55%；CPU≤20%；带宽≥36400 kbps | 2 次 |
| 1080p60 | 1920×1080@60 | 8000 kbps（5000–12000） | 不低于 15000 kbps | 帧率<54；p95>90ms；丢包≥5%；GPU>70%；CPU>30%；带宽<15000 kbps | p95≤70ms；丢包<1%；GPU≤50%；CPU≤20%；带宽≥19500 kbps | 2 次 |
| 1080p30（地板） | 1920×1080@30 | 4000 kbps（2500–6000） | 不低于 8000 kbps | 不降分辨率：带宽不足时码率压到 2500 kbps 并上报告警 | p95≤60ms；丢包<0.5%；GPU≤50%；CPU≤20%；带宽≥19500 kbps | — |

自动降级规则：

- 降档只降一档，降档后清空判据窗口；回升每次只升一档，带宽需留 30% 余量，防止档位抖动。
- 每会话自动切换总上限 6 次，同一档位最多进入 2 次；达到上限即锁定当前档位，只接受人工指定。人工指定不计入自动切换次数，且停止自动升降；再次下发 `auto` 恢复自动。
- `auto` 起步 1080p60，稳定 10 秒后逐档回升；不直接以 4K60 起步，避免建连首帧风暴。
- 降档与回升全部写入 `quality_events`，字段为 `ts`、`from`、`to`、`reason`、`metric`、`value`、`threshold`、`window_ms`，只保留最近 32 条，经 `get_session_metrics` 可读，不落库。
- 采样来源：帧率取渲染回调计数；p95 取端到端时间戳差值；丢包取序列号缺口；GPU 与 CPU 取平台计数器；带宽取发送队列与 RTT 估算。
- 中继通路不套用本表，按 L0 至 L3 降档；中继任何时刻不得承载 4K60。
- 硬件受限未验证：4K60 硬编复测与 240fps 延迟取证当前不可得，报告只能写「未验证」，不得写成通过；1080p30 地板已由 P0-03 实测（软编口径）。

### 3.11 Python 主栈下的各端技术取舍

| 端 | Python 承担 | 原生边界 | 界面 | 打包 | 取舍理由 |
|---|---|---|---|---|---|
| Windows | 命令、会话、信令、传输、媒体编排、指标 | DXGI 采集与 FFmpeg 桥用 C 模块经 C ABI 接入；UDP 热路径必要时用 Rust | PySide6 | Nuitka 生成 EXE/MSI | Python 迭代快；采集与编码是硬实时边界，放给 C 模块，避免 GIL 与 Python 对象开销 |
| macOS | 同上 | ScreenCaptureKit 用 Obj-C/C 模块；编码用 VideoToolbox C ABI | PySide6 | Nuitka 生成 DMG，签名与公证 | macOS 采集权限与硬件编码必须走系统框架，Python 只做编排 |
| Linux | 同上 | X11 XShm 与 PipeWire 用 C 模块；VAAPI 经 FFmpeg C ABI | PySide6 | Nuitka 生成 AppImage 与 deb | Wayland 限制多，保留 Xorg 完整路径，Wayland 走门户并标注限制 |
| Android | 命令、会话、信令、传输、控制逻辑 | Kotlin 薄壳负责 Activity、SurfaceView、MediaCodec、权限、前台服务；Python 经 Chaquopy 在同进程运行 | Kotlin 薄壳承载的最小界面 | Gradle 生成已签名 APK，侧载安装，不出 AAB、不上架 | 侧载只要求 APK 可直接安装，去掉商店合规与分发约束；硬解与 Surface 仍必须原生，Python 负责可复用逻辑 |

Android 形态说明：

- **分发形态：只做侧载 APK。** 不做 Google Play 与其他商店的合规、上架、AAB 与政策审查；安装包直接给用户安装。应用标识与签名一次定死，后续升级必须同签名，否则只能卸载重装。
- 签名与构建：Gradle 生成 release APK，使用项目自有 keystore（PKCS12，RSA 3072，有效期 25 年），keystore 与口令不进仓库、不进日志、不进构建摘要，由 O01 保管、S01 复核；构建输出 SHA-256 校验和写入发布记录。
- 安装引导：首次安装需在系统设置允许「安装未知应用」；安装后首次启动申请通知权限（Android 13 及以上）与网络权限，开始会话时启动前台服务（`connectedDevice` 类型）并在通知栏显示会话状态。Android 只作控制端：不申请 MediaProjection、不做屏幕采集、不做无障碍注入。厂商 ROM 的电池优化与后台限制给出图文引导。
- 最低版本：Android 10（API 29），targetSdk 34。
- **ABI 取舍（v1.3 修订）：只发 arm64-v8a，不增加 x86_64 ABI。** 理由：单一 ABI 与真机产物一致，避免双架构打包与 Chaquopy 双 ABI 依赖。验证口径改为 x86_64 系统镜像的模拟器：ABI 配置不动（APK 仍是 arm64-v8a），模拟器侧只验证「装得上、授权通过、能起前台服务、连接页可用、横竖屏切换」等功能链，**不验证该 APK 在 x86_64 模拟器上的安装**——当前 emulator 37.2.13 在无硬件加速的 x86_64 主机上无法完成 x86_64 API 34 镜像启动（TCG 路径卡死或 0xC0000005），该 AVD 已实测不可用，证据见 `D:\RDC-Build\evidence\poc\android\emulator-attempts.json`。**当前 emulator 版本不支持 x86_64 主机上的 arm64 AVD**，因此模拟器侧不产出任何性能数据；安装、连接、旋转与坐标映射的结论只能来自真机，模拟器数据一律标「x86_64 模拟器口径，性能不作基线」，帧率、延迟与 CPU 数据不得当作性能结论。真机补测项保留。
- 横竖屏：旋转时由 Activity 重建 Surface 并交回 MediaCodec 输出，解码会话不重建；方向与远端坐标系以 `display_update` 的 width、height、rotation 为准做映射，缺该消息时按 `session_start` 的方向处理，不得断流。
- **Chaquopy 与 Kivy 重新评估（以侧载可用为前提）**：侧载去掉了商店对解释器、AAB、64 位与政策的约束，但没有改变许可证问题。Chaquopy 仍为首选：Python 业务代码复用率最高，MediaCodec 经 Surface 零拷贝硬解，Kotlin 壳层可压在 2000 行内。若 S01 判定 Chaquopy 许可证不可接受，或构建链在侧载包上不可复现，回退 Kivy（python-for-android）：仍可侧载，但硬解需经 pyjnius 自行桥接，指标降为 720p30 软解，并在后续版本记录取舍。
- 若 Kotlin 壳层代码超过 2000 行或出现复杂业务逻辑，由 M01 报批补移动端岗位，不把壳层悄悄扩成第二主栈。

### 3.12 开源参考结论

完整横评见 `.team/records/开源对标横评-研究-202611-001-20261110.md`，其中逐项目、逐平台给出功能、界面、受众、采集实现、版本或提交日期、许可证与来源 URL。本节只记与本设计书直接相关的结论，不重复横评表格，也不复制任何上游代码。

- Windows 采集：RustDesk 的 DXGI Desktop Duplication 路线最完整（`DuplicateOutput1` 优先、失败回退 `DuplicateOutput`、GDI 兜底、dirty/move rect 与光标元数据），作为本项目 Windows 采集的行为参照；需要按窗口采集时，OBS 的 Windows.Graphics.Capture 实现是更稳妥的参照。
- macOS 采集：新项目应直接用 ScreenCaptureKit；RustDesk 仍在用已被 Apple 列为弃用的 CGDisplayStream，不作为参照。OBS 的 ScreenCaptureKit 实现可作为迁移样本。
- Linux 采集：通用与 Wayland 场景参照 RustDesk 的 X11 XShm 加 PipeWire/portal 双路径；追求最低延迟且限定 NVIDIA/X11 时参考 Sunshine 的 KMS/NvFBC 路径；纯 X11 存量环境以 TigerVNC 的 XShm 加 XDamage 加 XFixes 工程划分最规范，x11vnc 已缺维护。
- Android 采集：scrcpy 的 MediaProjection + VirtualDisplay/SurfaceControl 加 MediaCodec Surface 零拷贝是标杆，但 SurfaceControl 路径依赖 shell 权限；本项目产品化只走 MediaProjection，不复制其实现。
- 编码与协议：Sunshine/Moonlight 的参数取向（硬件编码优先、零延迟、无 B 帧）作为 3.6 的依据；不采用其 GameStream 协议栈。WebRTC 系（Janus、mediasoup、libwebrtc）在 Windows 屏幕采集仍以 DXGI 为主、WGC 只用于窗口，macOS 已引入 ScreenCaptureKit；本项目不引入完整 WebRTC 栈。
- 许可证：RustDesk 为 AGPL-3.0，Sunshine 与 Moonlight 为 GPL-3.0，x11vnc 与 TigerVNC 为 GPL-2.0，OBS 为 GPL-2.0，Janus 为 GPL-3.0，mediasoup 为 ISC，libwebrtc 为 BSD-3-Clause，scrcpy 为 Apache-2.0。上述项目一律只作方向与行为参照，禁止代码级复用与链接；任何例外须先由 S01 出具许可证结论，再经 M03 批准契约变更。

### 3.13 一套技术做四端：复用边界与新增代码

结论：**「一套技术做四端」成立，但只在协议与业务层成立；采集、硬编硬解、输入注入、渲染 surface 必须平台原生。** 复用的判断标准是「是否与操作系统 API 绑定」，不是「是否用 Python 写」。

| 层 | 是否复用 | 具体内容 | 依据 |
|---|---|---|---|
| 协议与线格式 | 完全复用 | 七字段包络、13 类信令消息、中继数据面、错误码 | 纯数据定义，与平台无关 |
| 信令与会话 | 完全复用 | 注册、挑战、认证、offer/answer/candidate、会话状态机 | 只依赖网络与密码学 |
| 加密与身份 | 完全复用 | Ed25519、X25519、HKDF、ChaCha20-Poly1305、SPAKE2 | 纯算法，四端同一实现 |
| 编码参数与画质策略 | 完全复用 | 档位表、码率区间、AIMD、降级与切换规则 | 输入只有通路、带宽、硬件能力三项 |
| 命令层契约 | 完全复用 | `CommandResult`、13 个命令函数、错误码 | 界面层唯一调用面 |
| 指标与日志 | 完全复用 | 指标口径、结构化日志、脱敏规则 | 与平台无关 |
| 桌面 UI | 三端复用 | Windows、macOS、Linux 共用 PySide6 界面 | Android 不支持 PySide6，必须原生 |
| 采集 | 不复用 | DXGI/WGC、ScreenCaptureKit、X11/PipeWire、MediaProjection | 各自系统 API 与权限模型不同 |
| 硬编硬解 | 不复用 | NVENC/QSV/AMF、VideoToolbox、VAAPI、MediaCodec | 驱动与 API 不同，只能各自绑定 |
| 输入注入 | 不复用 | SendInput、CGEvent、XTEST/uinput、MotionEvent | 权限与坐标模型不同 |
| 渲染 surface | 不复用 | D3D11/D3D12、Metal、EGL/GL、SurfaceView | 与窗口系统绑定，零拷贝路径不可移植 |
| 权限与服务生命周期 | 不复用 | TCC、UAC、portal、MediaProjection/前台服务 | 合规与授权流程各不相同 |

复用比例的口径与目标：

- 口径：以 `cloc` 统计 `src/rdc/` 与 `src/platform/`、`native/`、`android/` 的非空代码行，排除生成代码、第三方代码与测试；每批收工记录一次比例，写入验收报告。
- 目标：v1.0 时代码复用率不低于 65%（共享 Python 核心占全部自研代码行）；Android 的 Kotlin 壳层不超过 2000 行；各平台原生采集与编码模块只做「取帧、编码、解码、呈现、注入」五件事。
- 新增代码边界：共享逻辑只能进 `src/rdc/`，平台实现只能进 `src/platform/<os>/`、`native/` 与 `android/`；平台目录不得出现业务状态机，共享目录不得出现系统 API 调用。违反边界即由 M03 退回。

落地风险：复用比例是结果不是前提。若某端原生层膨胀导致比例低于 65%，由 M03 评估是边界划分问题还是平台差异，不得靠把业务逻辑下移到原生层凑比例。

### 5.3 信令与中继线协议 v1

包络字段固定为七项：

```json
{
  "v": 1,
  "type": "offer",
  "id": "6f1c2a9e-3b7d-4c1a-9e2f-0a1b2c3d4e5f",
  "session_id": "8a7b6c5d-4e3f-2a1b-9c8d-7e6f5a4b3c2d",
  "ts": "2026-11-10T10:00:00+08:00",
  "payload": {},
  "sig": "base64-ed25519-signature"
}
```

签名口径：UTF-8、键名排序、无多余空白的规范 JSON；`sig` 字段本身不参与签名；服务端校验设备公钥与时间窗口。

| 消息类型 | 方向 | 必填 payload 字段 | 用途 |
|---|---|---|---|
| register | 客户端 → 信令服务 | `device_id`、`public_key`、`capabilities`、`protocol_version` | 注册设备公钥与能力 |
| challenge | 信令服务 → 客户端 | `nonce`、`expires_at` | 下发一次性挑战 |
| auth | 客户端 → 信令服务 | `device_id`、`signature` | 证明持有设备私钥 |
| auth_ok | 信令服务 → 客户端 | `token`、`expires_at`、`relay_endpoint` | 签发短期令牌与中继端点 |
| offer | 控制端 → 信令服务 → 被控端 | `session_id`、`candidates`、`media_caps`、`access_proof` | 发起会话与候选交换 |
| answer | 被控端 → 信令服务 → 控制端 | `session_id`、`chosen_candidate`、`media_caps` | 接受会话与选择路径 |
| candidate | 双向经信令服务 | `session_id`、`kind`、`address`、`port`、`priority` | 增量候选 |
| relay_allocate | 控制端或会话发起方 → 信令服务 | `session_id`、`requested_kbps`、`est_duration_s` | 申请中继预算 |
| relay_allocated | 信令服务 → 请求方 | `session_id`、`relay_token`、`endpoint`、`budget_kbps`、`quality_profile` | 返回中继分配 |
| session_start | 双向经信令服务 | `session_id`、`transport_kind`、`quality_profile` | 通知会话开始 |
| session_end | 双向经信令服务 | `session_id`、`reason` | 通知会话结束 |
| heartbeat | 双向 | `session_id`、`seq`、`ts` | 保活与 RTT 采样 |
| error | 双向 | `code`、`message` | 统一错误，不带异常类名与堆栈 |

中继数据面：

- 控制连接走 TLS 1.3，使用中继令牌认证；令牌绑定会话、设备、预算与过期时间。
- 中继只转发 AEAD 密文与最少元数据，不解析屏幕、输入与剪贴板内容。
- 每个会话的预算取自 `RelayPolicy`；超出预算由中继拒绝或触发客户端降档，不在协议里写死码率。

## 七、技术栈与选型理由

| 类别（语言/框架/库/存储/构建/部署） | 选型 | 理由 | 被否决方案与被否决理由 | 是否花钱或占用资源 |
|---|---|---|---|---|
| 语言 | Python 3.12 | 用户指定 Python 主栈；生态覆盖网络、加密、FFmpeg 绑定与测试；迭代速度快 | Rust 重写：性能好但违背技术栈要求且开发周期长；C++：内存与构建复杂度高，团队无 C++ 主线 | 否 |
| 桌面界面 | PySide6 6.x | Qt 6 跨 Windows、macOS、Linux 一致；支持 OpenGL/RHI；LGPL 可动态链接 | Tkinter：渲染与高 DPI 弱；Electron：引入 Node 与 Web 栈，违背 Python 主栈；Kivy 桌面：非原生观感 | 否 |
| Android 形态 | Chaquopy + Kotlin 薄壳 | 硬件 MediaCodec 与 SurfaceView 是低延时刚需；Python 核心同进程运行；Kotlin 只做壳 | Kivy 纯 Python：只能软解，UI 非原生，硬解桥复杂；Flutter：引入 Dart 主栈；BeeWare：视频与硬解生态不成熟 | Chaquopy 许可证待 S01 复核；若需商业授权命中四类升级·花钱或占用资源 |
| 采集 | Windows DXGI、macOS ScreenCaptureKit、Linux X11 XShm 与 PipeWire，C/Obj-C 模块经 C ABI | 系统级采集延迟最低；可控帧时间戳与脏区；避免 Python 截图库的拷贝与编码开销 | mss/PIL 截图：拷贝多、帧率低；VNC 服务端：协议与画质不满足；Electron desktopCapturer：引入 Web 栈 | 否 |
| 编码 | FFmpeg 7.x LGPL 构建，硬件编码优先，OpenH264 兜底 | 一套 API 覆盖 NVENC、QSV、AMF、VideoToolbox、VAAPI、MediaCodec；硬件编码降低 CPU 与延迟 | GStreamer：管线复杂、打包体积大；自研编码器：成本高；默认捆绑 libx264：GPL 污染 | 否；S01 复核构建参数 |
| 传输 | asyncio UDP 直连加 AEAD 握手；中继走 TLS 1.3 | Python asyncio 足够编排；UDP 可做打洞与低延迟；中继 TLS 穿防火墙 | QUIC：Python 生态与调试成熟度不足；WebRTC 全栈：依赖重、许可与调优复杂；纯 TCP 直连：队头阻塞 | 否 |
| 信令 | WSS 加 JSON v1 | 443 端口易穿企业防火墙；JSON 可读、易取证；版本字段可扩展 | 裸 TCP：易被拦截；gRPC：依赖重、调试成本高；HTTP 轮询：延迟高 | 否 |
| 加密 | cryptography、PyNaCl、SPAKE2 | 标准原语齐全；Ed25519、X25519、ChaCha20-Poly1305 可用；PAKE 避免口令传输 | 自研加密：不可接受；明文口令挑战：易离线爆破；仅 TLS：中继可见明文 | 否 |
| 配置 | TOML 加环境变量 | 带宽、端口、端点、构建路径全部可配置；便于切换中继与部署 | 代码常量：换中继要改代码，违反可替换要求；纯命令行：桌面端不可用 | 否 |
| 打包 | Nuitka 加平台安装包；Android 用 Gradle | Nuitka 生成原生可执行，启动与反编译表现好；平台安装包支持升级与回滚 | PyInstaller：启动慢、易被误报；zipapp：依赖外部 Python，不适合终端用户 | 否 |
| 中继 | 现有 ECS 出口 3 Mbps，配置驱动，准入与 720p 降档 | 不新增采购即可验证降级链路；预算与档位可配置，后续可换自建或云主机 | 固定 3 Mbps 写死：换机器即失效；首版多中继集群：超出范围 | 占用现有 ECS 出口 3 Mbps；扩容命中四类升级·花钱或占用资源 |
| 测试 | pytest、pytest-asyncio、pytest-qt、tc netem、240fps 摄像取证 | 单元与集成可自动化；网络损伤可复现；端到端延迟有客观证据 | 只做手工点点：无法复现指标；只看日志：无法证明输入到画面延迟 | 否 |
| 日志与指标 | 结构化 JSON 日志，本地指标，默认不外传 | 按 10_日志 脱敏；用户隐私优先；问题可本地取证 | 默认云端遥测：隐私与合规风险；纯文本日志：难检索 | 否 |
