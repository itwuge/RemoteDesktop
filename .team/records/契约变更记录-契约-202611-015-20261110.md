# 契约变更记录 · 屏幕墙归属登记消息与落盘（protocol-v1 v1.5）

| 项 | 内容 |
|---|---|
| 变更编号 | 契约-202611-015 |
| 日期 | 2026-11-10 |
| 版本 | protocol-v1 v1.4 → v1.5；desktop-v1 不变 |
| 类型 | 非破坏性：新增 2 类消息与 1 个错误码；只增不删 |
| 提出方 | 信令与中继线（A6 屏幕墙越权验证缺正向对照） |
| 裁决 | 契约先行：消息先入表，信令线按表实现处理器与落库；归属写账号库，不写进程内存 |

## 1. 增量内容

| 消息 | 方向 | 必填字段 | 说明 |
|---|---|---|---|
| `wall_bind` | 被控端 → 信令服务 | wall_id、session_id | 登记屏幕墙归属；必须已认证并验签，且发送方是该会话的被控端 |
| `wall_bound` | 信令服务 → 被控端 | wall_id、account_id、bound_at | 登记结果；幂等重复上报返回首次 `bound_at` |

新增错误码：`WALL_OWNERSHIP_CONFLICT`（同一 `wall_id` 已归属其它账号，保留原绑定）。

语义要点：

- 账号只由服务端按已认证 `device_id` 从账号库解析，payload 自报账号一律不采信。
- host 判定沿用现有协议语义：`answer` 的成功发送方即被控端；`wall_bind` 要求发送方在该会话参与者内且等于已记录的 host，否则 `AUTH_FAILED`。
- 同墙同账号重复上报幂等；同墙换账号明确拒绝，不静默覆盖。
- 归属写入 `accounts.db` 的 `walls` 表，服务重启后仍生效；成功与冲突都写 `wall.bind` 审计（含 `wall_id`、`account_id`、`bound_by_device_id`、结果与原因）。

## 2. 兼容性

- 只新增消息类型、必填字段与错误码，既有消息字段和语义不变；旧客户端不发送 `wall_bind` 时行为不变，未登记归属的墙继续按 `SCOPE_INSUFFICIENT` 拒绝。
- 服务端账号库 schema v2 → v3：只新增 `walls` 表，使用 `CREATE TABLE IF NOT EXISTS`，重复启动或重复迁移不重建、不清旧数据，`walls` 行保留。

## 3. 部署与备份影响

- relay 单元新增 `StateDirectory=rdc-relay`（0700）与 `RDC_DATA_DIR=/var/lib/rdc-relay`，满足 `ProtectSystem=strict` 下的落盘要求；signaling 单元原已有 `StateDirectory=rdc-signaling`。
- `deploy/backup.sh` 归档 `/var/lib/rdc-relay`、`/var/lib/rdc-signaling`（含 `accounts.db` 与 WAL），drill 增加 `DRILL_ACCOUNTS_DB` 校验 `user_version=3` 与 `walls` 行数；不归档会在恢复演练中丢墙归属。

## 4. 回滚

- 代码回滚到 v1.4 后服务端不再识别 `wall_bind`/`wall_bound`，客户端发送返回 `UNKNOWN_TYPE`；`walls` 表保留但不参与鉴权，未登记归属的墙按原口径拒绝。
- 账号库保持 v3 结构，旧程序读取 v3 会因版本高于自身而拒绝打开；回滚前需将 `PRAGMA user_version` 置回 2 并保留 `walls` 表（或恢复部署前备份）。生产回滚按发布流程执行，不在服务运行中直接改库版本。

## 5. 验证路径（A6 正向对照）

脚本 `scripts/verify_wall_bind.py` 覆盖完整序列：

1. 真实账号 A、B 各自 `register → challenge → auth → auth_ok`。
2. 会话 S1：B 发 `offer`、A 回 `answer`（A 为 host），A 发 `wall_bind` → `wall_bound`。
3. A 重复上报同一 `wall_id` → `wall_bound` 且 `bound_at` 不变（幂等）。
4. A `wall_preview` 自己的墙 → `wall_preview_granted`。
5. B `wall_preview` 同一墙 → `SCOPE_INSUFFICIENT`（越权被拒）。
6. A 再次 `wall_preview` → 仍 `wall_preview_granted`（原账号可用）。
7. 会话 S2：A 发 `offer`、B 回 `answer`（B 为 host），B 对同墙 `wall_bind` → `WALL_OWNERSHIP_CONFLICT`，原归属不变。
8. 反向：未认证连接发 `wall_bind` → `AUTH_FAILED`；会话内非 host 参与方发 `wall_bind` → `AUTH_FAILED`。

## 6. 已执行与本机证据

- 本机以真实 `python -m rdc.relay` 进程（明文 TCP、`RDC_ACCOUNTS_DB` 指向临时持久库）跑通 `scripts/verify_wall_bind.py prepare → verify`：11 项全 PASS，另在重启进程后以 `--expect-existing` 复跑 12 项全 PASS，`bound_at` 前后一致。
- 落盘核对：`PRAGMA user_version=3`；`walls` 表 1 行；`audit` 表 `wall.bind` 依次出现 `created`(ok)、`unchanged`(ok)、`conflict`(fail)，字段含 `wall_id`、`account_id`、`bound_by_device_id`、`reason`、`existing_account_id`。
