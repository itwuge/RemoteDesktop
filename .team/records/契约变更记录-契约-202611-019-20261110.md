# 契约变更记录（桌面端账号页 UI 收口缺口）

## 一、基本信息

| 字段 | 填写要求 | 填写内容 |

| 变更编号 | 唯一编号，建议「契约-年月-序号」，如 契约-202611-001 | 契约-202611-019 |
| 涉及契约与版本 | 契约名称 + 变更前版本 → 变更后版本 | desktop-v1 v1.3 → v1.3（仅登记缺口，正文未改）；protocol-v1 无变更 |

| 批准人 | 填写批准岗位与姓名/编号（接口文件改动必须为 M03 架构师） | 待 M03 架构师裁决（本记录只登记，不改契约正文） |
| 关联提交号 | 填写实际提交号；尚未提交则写「待提交」 | 待提交 |
| 状态 | 待批准 / 已批准待提交 / 已完成 / 已回滚 | 待批准 |

> 触发来源：桌面端账号页按 `docs/design/ui-v2/` 收口（r6）。以下缺口只登记，不修改 `docs/contracts/desktop-v1.md` 正文，也不在界面侧自造字段。

## 二、背景与动因

| 项目 | 填写内容 |
|---|---|
| 触发来源（对应需求条目编号或缺陷编号） | 桌面端 UI 严格自查（账号页批次），用户指示「C 类契约缺口只登记不改正文」 |
| 为什么必须改（不改会怎样） | 账号页需要呈现「找回/重置口令」与「设备令牌掩码」两处能力；当前契约既无命令也无字段，界面只能留空或不提供入口，用户可能误判为功能缺失 |
| 备选方案与未采用原因 | 方案 A：界面本地拼装掩码——未采用，界面拿不到令牌原文，且违反 `get_account_state()` 白名单；方案 B：找回口令走离线邮件/客服——未采用，涉及服务端身份校验，必须先有契约 |

## 三、缺口清单

| 序号 | 缺口 | 现状 | 影响界面 | 建议补法（待 M03 裁决） |
|---|---|---|---|---|
| C1 | 账号找回 / 重置口令无命令 | `rdc.commands.accounts` 只有 `register_account`、`login_account`、`refresh_session_token`、`logout_account`；`界面说明.md` §5 与原型均无找回入口 | 账号页无法提供「找回口令」；本版按原型不设入口，空态与错误文案不涉及该路径 | 新增 `accounts.request_password_reset(account)` 与 `accounts.reset_password(account, code, new_password)`，或明确 v1 不提供并写进界面说明 |
| C2 | 设备令牌掩码无字段 | 契约-202611-018 §6.2.2 规定 `get_account_state()` 白名单不含任何令牌 | 账号页「设备令牌」只能显示「未签发 / 已签发」，不能显示首尾各 4 位掩码 | 在 `get_account_state()` 白名单新增 `device_token_masked`（只读、不可逆、固定 4+…+4 格式），或明确界面不展示掩码 |
| C3 | 登录失败错误码上屏口径 | `error_text()` 已把错误码翻成中文原因，`CREDENTIAL_INVALID` 统一提示「账号或口令不正确」 | 无阻塞；需确认错误码本身是否允许出现在界面提示的附属说明里 | 建议维持「只上屏中文原因，错误码仅进日志」，并在说明文档固化 |

## 六、受影响的接口与数据结构

- C1：`rdc.commands.accounts` 新增找回/重置命令；涉及服务端 `POST /v1/accounts/password/reset`（新增接口需在契约-202611-018 §6.1 基础上追加）。
- C2：`rdc.commands.accounts.get_account_state()` 返回 data 新增 `device_token_masked`；不得返回 `device_token`、`session_token` 原文。
- C3：不新增字段；仅固化错误码上屏口径。
