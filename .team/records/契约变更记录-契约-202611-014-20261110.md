# 契约变更记录 · 文件与剪贴板接入会话通道（desktop-v1 v1.8 / protocol-v1 v1.6）

| 项 | 内容 |
|---|---|
| 变更编号 | 契约-202611-014 |
| 日期 | 2026-11-10 |
| 版本 | desktop-v1 v1.7 → v1.8；protocol-v1 v1.5 → v1.6 |
| 类型 | 非破坏性：新增命令 50、新增协议消息 1 类、新增 3 个错误码、补充语义；第 32 至 40 条签名不变 |
| 提出方 | 文件与剪贴板线（缺口 19、20：进度条显示已到达但实际未跨端） |
| 裁决 | 先登记契约与协议，再合入通道实现；host 侧接线另行排期，不在本次改动范围 |

## 1. 缺口与裁决

| 缺口 | 裁决 |
|---|---|
| 缺口 19：文件传输只在本机落盘复制 | 文件传输接入会话通道：分块发送、收端按 `.part` 落盘、逐块 sha256 与整树摘要校验、`file_result` 回执、断点续传、4 MiB 在途背压；发送端只有 `verified=true` 才置 `completed` |
| 缺口 20：剪贴板只在命令层内存同步 | 剪贴板接入同一通道：`clipboard_update`/`request`/`ack` 双向同步，同摘要去重，开关关闭即拒绝；`push` 在对端 ack 前只显示「等待对端确认」 |
| 收端无法告知发送端校验结果 | 新增 `file_result`（第 10 类会话数据面消息），`verified` 与 `digest` 必填，失败必须带 `error_code` |
| 续传偏移无出处 | `file_accept.resume` 明确为续传偏移列表，由接收端按本地 `.part` 实际长度给出；发送端不得自行假设 |
| 用户误以为已到达 | 第 50 条暴露通道状态；降级通道必须在页面显示「对中继可见、未达端到端加密」，`local_staging` 显示「只在本机复制」 |
| 通道写死在中继分支 | 文件与剪贴板只依赖 `SessionChannel` 抽象（open/send/receive/close/info）；后续正式数据面会话密钥可直接替换 |

## 2. 协议增量（protocol-v1 v1.6）

- 新增 `file_result`：接收端 → 发送端，必填 `session_id`、`transfer_id`、`verified`、`digest`，可选 `error_code`、`error_message`。
- `file_offer` 的 `digest`（整树摘要）由隐含约定改为必填字段，与 `file_result` 校验闭环。
- `file_accept.resume` 明确为 `[{relative, received_bytes}]` 列表，语义为收端已落盘前缀。
- 3.1 顺序追加 `file_result`；新增第 4 条：发送端未收到 `verified=true` 前界面不得显示完成。
- 新增 3.4 节：整文件校验、逐块校验、续传、背压（4 MiB 在途、30 秒确认超时）、通道可替换、降级通道可见性与「未达端到端加密」。
- 未新增协议版本号字段变化：顶层 `v` 仍为 1，只做非破坏性增量。

## 3. 命令增量（desktop-v1 v1.8）

| 序号 | 命令 | 说明 |
|---|---|---|
| 50 | `get_transfer_channel_status()` | 返回 `bound`、`kind`、`session_id`、`encrypted`、`visible_to_relay`、`budget_kbps`、`mode`；`mode` 取 `channel`、`local_staging`、`unbound` |

- 第 37 至 40 条签名不变；`status` 的 data 允许附加只读通道与确认字段（`mode`、`bound`、`pending`、`confirmed` 等），见 3.10 节。
- 新增错误码：`SESSION_CHANNEL_UNAVAILABLE`、`SESSION_CHANNEL_TIMEOUT`、`CHANNEL_BACKPRESSURE`。
- 第 32 至 36 条语义补充：`completed` 以 `file_result(verified=true)` 为准；`phase=verifying` 显示「等待对端校验与确认」。

## 4. 缺口关闭依据

### 缺口 19（文件传输跨端）

- 跨进程实测（本机真实 TCP + `RelayDataPlane`，relay/sender/receiver 三个独立 OS 进程）：2,097,152 字节，0.250 秒，8,388 KB/s，整树摘要 `e00eecbf…302e13`，收端真实写入磁盘且内容 SHA-256 `91d3beb8…bd1938` 与源一致，6 项校验全过。证据：`evidence/file-channel-20261110-*/`。
- 单测覆盖：续传（预置 200,000 字节 `.part`，实发 500,000）、块篡改失败、4 MiB 在途窗口、ack 超时、无通道拒绝、路径穿越拒绝、空文件。
- 关闭判据：`completed` 只在收端回 `verified=true` 且摘要一致后成立；失败有明确错误码，不会停在进度条。
- **未达端到端加密**：本版走信令降级通道，`file_chunk` 载荷对中继可见，不满足 3.1 节「必须使用会话密钥加密」的最终要求；该项另行排期，缺口 19 按「跨端可用但未加密」关闭。

### 缺口 20（剪贴板双向同步）

- 跨进程实测（relay/desktop/android 三进程）：双向文本推送摘要互等、反向拉取内容逐字一致、重复推送抑制、关闭后拒绝发送、两端 `visible_to_relay=true` 且 `status` 不含正文，12 项校验全过。证据：`evidence/clipboard-channel-20261110-182043/`。
- 单测覆盖：双向推送与 ack、去重、拉取、对端无内容报 `CLIPBOARD_EMPTY`、关闭开关、状态不含明文、摘要不符拒绝。
- 关闭判据：`push` 在对端 ack 前为 `pending`；`status` 只有摘要与长度。
- **未达端到端加密**：同缺口 19，降级通道对中继可见。

## 5. 需要其它线跟进

| 线 | 跟进项 | 验收 |
|---|---|---|
| host 接线（用户统一排期） | 在会话建立处调用 `FileTransferService.bind_channel(...)` 与 `ClipboardSyncService.bind_channel(...)`；消息泵把通道帧交给 `FileTransferReceiver.handle` / `ClipboardReceiver.handle`，回包写回通道 | 桌面与 Android 各传 1 个文件、互发 1 段文本；页面显示降级提示 |
| 数据面会话密钥 | 提供 `SessionChannel` 的加密实现，替换 `RelayFrameChannel`，`encrypted=true` | 同场景下页面不再显示「对中继可见」 |
| 信令与中继线 | `server.py` 已加 `_handle_file_result` 转发；与 `wall_bind` 分支互不重排 | 双端互通，`wall_bind` 用例不回归 |
| 质量与证据 | 冒烟补通道状态与待确认口径 | 新增项区分实测/模拟/未验证 |

## 6. 未验证

- 公网条件、真实 Android 端与 4 GiB 大文件：未验证，仅本机回环与单测。
- 正式数据面会话密钥与端到端加密：未实现，本版明确「未达端到端加密」。
- 剪贴板图片在真实系统剪贴板间的写入：业务层只做校验与回调，系统写入由 host 接线完成。
