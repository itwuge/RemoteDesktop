# 无控制台启动与崩溃排查

面向 Windows 双击/快捷方式启动：不出现黑色控制台窗口，且任何未捕获异常都必须落盘并给用户可见提示，不允许静默消失。

## 一、结论先行

1. **已确认的根因（实测）**：`pythonw.exe` 在不继承控制台句柄时，`sys.stdout`、`sys.stderr`、`sys.stdin` 全部为 `None`；默认 `sys.excepthook` 无法写出堆栈，进程以退出码 1 结束，磁盘上没有任何异常记录，用户也看不到任何提示。这正是"无控制台 + 静默退出"的机制。
2. **不是 PATH 或解释器定位问题（实测）**：同一 `pythonw.exe` 能正常导入 `rdc` 并写出启动日志；问题在标准流缺失与异常钩子缺位，而不是找不到解释器或脚本。
3. **已修复（实测）**：包导入期补位标准流，启动时安装主线程/子线程/unraisable 异常钩子，异常写 `crash.log` 与 `rdc.log`，无 Qt 时用系统对话框提示；另加 `fault.log`、启动/退出事件与 10 秒心跳。
4. **带负载连续三轮未复现退出（实测）**：开发态 `pythonw -m rdc.ui` 与打包态 `rdc-desktop.exe` 各三轮、每轮 45 秒，负载为全量 pytest + 2 个 CPU 忙等进程；6 次全部存活至主动关闭，退出码 0，无 conhost、无子进程、无 Windows 应用程序错误事件（1000/1001/1002）。
5. **历史第 11 秒 / 第 30 秒退出（推断）**：现有证据无法复现，也无法归因到单一代码缺陷。若当时发生了 Python 异常，默认钩子会以退出码 1 静默结束且无日志，与现象吻合；若连崩溃事件都没有，则更可能是外部终止（并发构建/门禁清理进程、杀软、会话回收）。现在心跳、`app.exit` 与 `crash.log` 会在下次出现时留下可判定证据。

行为约定：

- 日志目录优先级：`RDC_LOG_DIR` > `RDC_BUILD_ROOT/logs/rdc` > 打包产物旁 `data/logs` > `./logs`；不可写时退系统临时目录。

## 四、复现方式

```powershell
# 机制实验（约 5 秒）
python scripts/diagnose_no_console.py

# 带负载连续三轮，开发态与便携包各一次（约 5 分钟）
python scripts/verify_no_console_stability.py --rounds 3 --duration 45 --target both

# 只测打包产物
python scripts/verify_no_console_stability.py --rounds 3 --duration 45 --target portable
```

手动观察：

```powershell
# 1. 看进程与日志
Get-Process pythonw, rdc-desktop -ErrorAction SilentlyContinue
Get-Content logs\rdc.log -Tail 20

# 2. 看 Windows 应用程序日志里的崩溃事件
Get-WinEvent -FilterHashtable @{LogName='Application'; StartTime=(Get-Date).AddHours(-1)} |
    Where-Object { $_.Id -in 1000,1001,1002 -and $_.Message -match 'pythonw|rdc-desktop' }
```

判定口径：

- `app.start` 有、`app.exit` 无、且无 `crash.log` → 进程被外部终止或原生崩溃，先看事件日志与 `fault.log`。
- `crash.log` 有 → 未捕获异常，堆栈直接可读。
- 两者都没有 → 进程可能根本没启动到 Python 层，检查入口路径与杀软拦截。

## 五、并发与句柄相关结论

| 关注点 | 实测 | 结论 |
|---|---|---|
| 标准输入输出句柄缺失 | 三者均为 `None`；直接写 `stderr` 抛 `AttributeError` 并退出 1 | 是静默退出的必要条件，已由补位消除 |
| 子进程继承 | `subprocess.Popen` 在无控制台父进程下可正常创建、等待，子进程 `stdout is None`、退出码 0 | 未发现继承导致失败；不再需要额外句柄处理 |
| 并发资源竞争 | 两进程写同一轮转日志丢 2480/3000 行，但两进程均正常退出 | 属日志完整性问题，不是进程退出原因；同一日志目录不要并发跑多个调试实例 |
| 带负载启动 | 6/6 次存活 45 秒，无崩溃事件 | 本轮未能复现历史退出 |

### 已知缺陷：并发写同一轮转日志会丢行

- 现象（实测）：两个进程对同一 `rdc.log` 各写 1500 行（`RotatingFileHandler(maxBytes=4096, backupCount=2)`），最终只剩 520 行，丢 2480 行；两个进程本身均正常退出（退出码 0）。
- 影响：真实并发下会丢排查线索，但不影响进程存活与退出码，不是本次静默退出的原因。
- 根因：轮转是"重命名 + 新建"两步，跨进程没有锁；两个进程交替轮转时互相覆盖备份文件。
- 评估与方案（本轮不改）：
  1. 按进程分文件 `rdc-<pid>.log`：改动最小，能立即隔离写冲突；代价是排查时需按 pid 找文件。
  2. 单实例约束（`QLocalServer`/命名互斥量）：第二个实例直接唤醒已有窗口后退出，从根上消除并发写，也更符合桌面客户端习惯；改动中等。
  3. 外部日志汇聚（文件锁或独立写日志进程）：能力最强但引入额外依赖，当前不必要。
- 建议：下一轮先落方案 1（低风险、可回退），若产品确定只允许单实例，再叠加方案 2。
- 取证优先级：`crash.log` > `fault.log` > `rdc.log`；多实例时先按 `pid` 字段区分再拼接时间线。

## 六、入口收敛

- 新增 `启动桌面端.vbs`：Windows Script Host 直接执行，不创建控制台；同目录存在 `rdc-desktop.exe` 时优先启动打包产物，否则用 venv 的 `pythonw.exe -m rdc.ui`。
- 删除 `启动桌面端.bat`，避免同一项目出现"一个有黑框、一个没有"的两个入口。
- `scripts/start_desktop.ps1` 保留安装检查职责，启动动作改为调用 `.vbs`。
- 面向最终用户：安装包快捷方式直接指向 `rdc-desktop.exe`；便携包解压后双击 `rdc-desktop.exe`。两者都是 `--windowed` 构建，本身不带控制台。

## 七、未决与后续

- 历史第 11 秒 / 第 30 秒退出未复现（实测），外部终止只是推断；下次出现时按第四节口径取证。
- 若后续确认是并发构建误杀，应在构建脚本中按进程名或命令行精确匹配，避免终止开发态实例。
