# 文件传输与剪贴板会话通道实测（2026-11-10）

## 1. 范围与结论

| 缺口 | 本轮结果 | 关闭依据 |
|---|---|---|
| 19 文件传输跨端 | 已打通：分块发送、收端落盘、逐块与整树摘要校验、`file_result` 回执、断点续传、4 MiB 在途背压 | 跨进程实测 2 MiB 文件校验全过；`completed` 只认收端 `verified=true` |
| 20 剪贴板双向同步 | 已打通：双向推送、对端 ack、去重、开关、反向拉取 | 跨进程双向实测 12 项全过；`status` 不含正文 |

限制：本轮走信令降级通道（`RelayFrameChannel`），**未达端到端加密**，文件内容与剪贴板载荷对中继可见；界面与日志已显式提示，正式数据面会话密钥另行排期。

## 2. 实测环境与方法

- 机器：Windows，Python 3（仓库默认解释器），本机回环 TCP。
- 装置：`scripts/verify_file_channel_e2e.py`、`scripts/verify_clipboard_channel_e2e.py`，均由编排进程拉起 relay / 收发两端三个独立 OS 进程，relay 使用产品代码 `rdc.relay.dataplane.RelayDataPlane`。
- 复现：

```
python scripts/verify_file_channel_e2e.py
python scripts/verify_clipboard_channel_e2e.py
```

约束核对：

- 传输逻辑仍全部走可 import 的 `FileTransferReceiver` / `ClipboardReceiver`，host 只做 `handle()` 与回包，不重写分块、校验、去重。
- 接收端在 AEAD 握手成功后才构造，空闲期不挂监听、不创建目录、不写盘；`FileTransferReceiver` 仅在收到 `file_offer` 后建 `.part`。
- 通道未被写死：消息只认数据面类型集合，不判断中继分支；换传输实现不影响分流。
- 单测 `tests/test_host_session_plane.py`（3 项）：输入消息不被会话面消费；`clipboard_update` 回 `clipboard_ack` 并自动补 `session_id`；无 offer 的 `file_chunk` 回 `file_abort` + `error_code`。

### 6.2 剪贴板双向（同一次会话）

| 方向 | 载荷 | 结果 |
|---|---|---|
| host → 桌面 | 发起前在虚机用 `xclip` 播种 `RDC-CLIP-HOST-2026`（18 字节，sha256 `a9f4d7c5…`） | 控制端 `clipboard_request` → 收到 `clipboard_update`，前缀逐字一致，耗时 189 ms |
| 桌面 → host | `RDC-CLIP-DOWN-2026`（18 字节，sha256 `9468a166…`） | host 回 `clipboard_ack applied=true`，耗时 26 ms；随后在虚机 `xclip -selection clipboard -o` 回读为同一字符串 |

**接线中发现并修掉的缺陷**：`_write_system_clipboard` 最初用 `capture_output=True`，`xclip` fork 出的常驻进程继承了管道，父进程已退出仍等不到 EOF，表现为每次写入稳定 2.0 秒超时（日志「xclip 写入失败: timed out」，但选区实际已写入）。改为 `stdout/stderr=DEVNULL` 后写入耗时 2019 ms → 26 ms，日志不再报失败。

### 6.3 Android 被控端 agent 接线（本机 TCP 模拟对端）

手机不在手边，本轮用本机真实 TCP + hs=2 双方握手 + `AeadChannel` 模拟控制端，被控端侧直接走 `run_host` 同一套接收端与 `handle_session_plane()`。装置为临时脚本（工作目录 `D:\RDC-Build\rdc-lan`，不入库）。

| 项 | 实测值 |
|---|---|
| 文件数 / 大小 | 3 个文件，171,200 字节（`a.txt` 120,000 + `dir/b.bin` 51,200 + `dir/空文件.txt` 0，含子目录与空文件） |
| 耗时 / 速率 | offer 到 `file_result` 21.8 ms，62.9 Mbps（32 KiB 分块、逐块等 ack，回环链路） |
| 整树摘要 | 控制端期望、`file_result.digest`、接收端本地重算三者一致，`verified=true`，无 `error_code` |
| 落盘位置 | `default_destination_root()`：`RDC_TRANSFER_DIR` 优先，否则 `%TEMP%\rdc-inbox`；实测落盘目录由 agent 启动时打印 |
| 落盘校验 | 3 个文件均存在且逐字节一致，无残留 `.part` |
| 剪贴板 桌面→手机方向 | 控制端 `clipboard_request` → `clipboard_update`，内容为会话开始时读入的本机剪贴板文本，0.3 ms |
| 剪贴板 手机→桌面方向 | `clipboard_update` → `clipboard_ack applied=true`，0.7 ms；重复同摘要回 `applied=false`（suppressed=1） |
| 无会话不建目录 | 只构造 `FileTransferReceiver` 不创建目录（实测 `created=False`）；目录与 `.part` 只在收到 `file_offer` 后出现 |
| 错误不静默 | 非法图片剪贴板回 `error CLIPBOARD_DECODE_ERROR`；无 offer 的 `file_chunk` 回 `file_abort FILE_CHUNK_INVALID`；`../evil.txt` 的 offer 回 `file_abort FILE_OFFER_REJECTED` |
| 本机剪贴板写入 | `write_system_clipboard("text", …)` 写入并回读一致；`kind=image` 显式抛 `RuntimeError`（Windows 侧未实现图片写入），日志可见 |

**方向与落盘责任（回答 §2）**：

- 本轮接通的是「安卓控制端 → Windows 被控端（agent）」：文件由 **agent**（Windows 进程）落盘，app 不参与落盘，目录即上面 `default_destination_root()`。
- 「桌面 → 安卓」方向目前没有落盘点：`android` app 0.3.5 只有渲染与输入，没有文件/剪贴板接收端，agent 也不承担发送。桌面若发起 `file_offer`，app 不会回 `file_accept`，传输会停在等待对端确认直到超时失败，不会静默当作成功。
- app 不支持时 agent 侧的行为：收到的每条会话面消息都有应答或错误帧；带 `type` 但不在 `SESSION_PLANE_TYPES` 内的消息会打印「忽略未知会话消息」，不做静默丢弃。
- 0.3.5 连上来只有 `pointer`/`key`/`gesture`（无 `type` 字段），分流不命中，行为与接线前一致；hs=2 握手与流媒体链路未改动。
