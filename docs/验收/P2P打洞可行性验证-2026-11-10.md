# P2P 打洞可行性验证报告

- 日期：2026-11-10
- 范围：UDP 打洞可行性、直连能力实测、回落中继设计建议、ECS 侧放行清单
- 约束：未重启任何设备、未改 ECS 配置、未改 `src/`、未改契约正文、未改 `android/`、未采购任何服务

## 一、结论摘要

| 场景 | 实测结果 | 依据 |
| --- | --- | --- |
| Windows 出口 NAT 类型 | endpoint-independent mapping（锥形） | 同一 UDP 端口向 2 个不同 IP 的 STUN 服务查询，映射地址完全一致：`115.150.84.112:41010` |
| 手机 Wi-Fi（与 PC 同一出口） | endpoint-independent mapping | 同上，映射地址 `115.150.84.112:41000` |
| Ubuntu 虚机（VMware NAT） | endpoint-independent mapping | 同上，映射地址 `115.150.84.112:49492` |
| 同 NAT 内两台设备打洞 | **失败**（手机与虚机两组均失败） | 双方各持续发包 16 秒，互收 0 包；家用路由器不支持 NAT 回环 |
| 同网段直连（host 候选） | **成功**（手机 Wi-Fi 组、虚机 VMnet8 组均成功） | 首包 1.4–98.1 ms，RTT p50 0.43–5.2 ms |
| 跨 NAT（家用宽带到移动 CGNAT） | **失败** | 手机侧映射端口随目的地址变化（52187 / 52190），即对称型 NAT；双向各发 159 包，互收 0 包 |
| 直连链路吞吐 | 40 Mbps 目标下 0% 丢包 | 手机组 38.1 Mbps；虚机组发送 39.94 Mbps、41605 包全收 |
| 1080p30 管线 | 编码 p50 约 10–12 ms、解码 29.6 fps | 既有实测，见 `evidence/quality-smoke3` |

结论分三句：

1. **能穿的组合**：两端都是锥形（endpoint-independent）NAT 时，具备打洞条件；本机出口已确认属于这一类。
2. **不能穿的组合**：任一端为对称型 NAT / 移动 CGNAT 时，打洞在物理上不可行，必须回落中继。
3. **同一个 NAT 内**：不要依赖公网地址回环（实测家用路由器直接丢弃），必须使用局域网 host 候选直连。

**连接优先级（2026-11-10 定稿，四端统一）**：IPv6 直连 → P2P 打洞 → 中继。当前第一级不可用（本机与家宽均无全局 v6，见七bis），第二级对移动 CGNAT 不可穿，因此「手机在外控家里电脑」现在实际落在中继；家宽开通 v6 后该场景可转为直连。策略细节见 [connect-v1.md](file:///c:/Users/Administrator/Desktop/RemoteDesktop/docs/design/connect-v1.md)。

**成功率判断依据**：本次只取得两个真实出口样本——一个锥形（家庭宽带）、一个对称（移动 CGNAT）。样本量不足以给出百分比成功率，也不应凭经验编造数字。可确定的判定规则是：

- 两端均为锥形映射 → 可穿（本次未取得第二个锥形出口，标记为未验证）；
- 任一端为对称映射 → 不可穿（本次已实测）；
- 两端同出口 → 公网地址回环不可用（本次已实测），改走 host 候选。

### 2.2 虚机接入方式（初版误判与修正）

初版曾判定虚机「不可执行代码」，原因是两处用法与扫描问题，虚机本身正常：

- 端口扫描只覆盖了 21/22/80/443/3389/5900 等常用端口，**漏掉了 22022**。实际 `22` 未开 sshd，`22022` 有另一条线的 sshd，`45900` 是 rdc-serve。本次改走 22022。
- `vmrun runProgramInGuest` 必须带 `-gu/-gp` 凭据且**不能带 `-interactive`**；带 `-interactive` 才会报「客户机用户必须以交互方式登录」。按正确写法复验：`runProgramInGuest` 写入 `/tmp/rdc_vmrun_check.txt`、`copyFileFromGuestToHost` 取回，两条命令退出码均为 0，内容 `vmrun_ok`。另外 `vmrun` 不回显客户机程序 stdout，需重定向到客户机文件再取回。

因此虚机组验证已补齐，见 4.4。真机 Android 一组保留：它提供「运营商 CGNAT」这一虚机不具备的真实对称型出口。

### 2.3 带外信令的等价说明

候选地址交换在 Windows↔Android 组通过 adb 文件通道完成、在 Windows↔虚机组通过 SSH/SFTP 完成，取代生产环境中的信令服务（`offer` / `answer` / `candidate`）。这只替换了「交换候选」的通道，不改变打洞本身的网络条件，因此对结论无影响。

虚机组已收进仓库脚本，可直接复现：

```
python scripts/p2p_holepunch_probe.py run-vm --mode lan --bulk-kbps 40000 --work evidence/p2p/<时间戳>
```

- 账号与口令只从环境变量 `RDC_VM_USER` / `RDC_VM_PASSWORD` 读取，脚本、证据、报告中均不出现；
- SSH 主机密钥按 SHA-256 指纹校验（环境变量 `RDC_VM_HOST_KEY_SHA256` 可选，未设置时仅记录到 `summary.json`），未使用自动信任未知主机密钥；
- 虚机只有一个出口（ens33 → VMware NAT → 家庭路由），因此**跨 NAT 组无法用虚机复现**，该项仍由 Android 移动数据承担。

## 三、分层现状与复用结论

### 3.1 现状

| 层 | 实现 | 传输 | 关键事实 |
| --- | --- | --- | --- |
| 信令 | `src/rdc/signaling/server.py`、`messages.py`、`envelope.py` | TCP + 4 字节长度帧 + JSON 包络 | 31 类消息；`offer`/`answer`/`candidate`/`session_start` 等属 `ROUTED_TYPES`，服务端按 `session_id` 转发 |
| 中继 | `src/rdc/relay/server.py`、`dataplane.py` | TCP（可选 TLS 1.3） | `relay_hello` + `relay_token` 鉴权，按 `session_id` 配对发布/订阅，令牌桶按预算限速 |
| 协议契约 | `docs/contracts/protocol-v1.md` | — | 已定义 `offer.candidates`、`candidate.kind`（host / srflx / relay）、`answer.chosen_candidate`、`session_start.transport_kind` |
| 质量档位 | `src/rdc/commands/service.py` | — | `transport_kind != "relay"` 时放开直连档位（含 4K60），中继仅允许 `RELAY_ONLY_PROFILES` |
| UDP | 无 | — | 全仓库 `src/` 中不存在任何 `SOCK_DGRAM` / UDP 代码 |

### 3.2 可直接复用

1. **信令包络与设备鉴权**：`register` / `challenge` / `auth` / Ed25519 签名、5 分钟时间窗、`id` 重试复用，全部与打洞无关，原样可用。
2. **候选交换通道**：`offer.candidates`、`candidate`、`answer.chosen_candidate`、`session_start.transport_kind` 已在契约与 `ROUTED_TYPES` 中就位，服务端已具备按会话转发能力。**打洞不需要改契约、不需要新增消息类型。**
3. **预算与降级**：`relay_allocate` / `relay_allocated` 的 `budget_kbps`、`quality_profile` 与 `RelayPolicy` 可直接作为回落目标的参数来源。
4. **会话密钥与媒体语义**：SPAKE2 派生 + AEAD 会话、`kind=video` 的字段语义（`w`/`h`/`fps`/`pts`/`seq`/`key`/`data`）可沿用。

### 3.3 必须新增

| 新增项 | 原因 |
| --- | --- |
| STUN 客户端（Binding 请求、XOR-MAPPED-ADDRESS 解析） | 现无任何 UDP，无法获得 srflx 候选 |
| host 候选枚举 | 需要列出本机各网卡的局域网地址（同网段直连实测有效） |
| NAT 映射/过滤行为探测 | 决定「是否值得尝试打洞」；本次已用验证脚本验证该做法可行 |
| 连通性检查（connectivity check） | 双向探针、优先级排序、失败判定 |
| UDP 数据面帧格式 | 现有 4 字节长度前缀是流式语义，UDP 每包必须自描述，且需处理大于 MTU 的关键帧 |
| 打洞失败回落状态机 | 现有代码只有中继一条路 |

### 3.4 不能直接复用

1. **4 字节长度帧**：TCP 流语义，UDP 下需要「包头 + 分片序号 + 重组」；1080p 关键帧必然大于单包 MTU，不分片无法传输。
2. **JSON + Base64 封装**：实测封装膨胀 1.36–1.53×。放到 UDP 上会直接放大分片数量与丢包代价，建议 UDP 路径改用二进制头 + 密文净荷。
3. **中继数据面**：`RelayDataPlane` 的配对、`relay_token`、令牌桶全部绑定 TCP 连接生命周期，不能平移到 P2P。

### 3.5 契约缺口（只记录，不修改）

1. 契约第六节只描述 TCP/TLS 中继数据面，**没有 UDP 数据面的帧格式、分片与重组、丢包反馈定义**。新增 P2P 通路需要 v2 增补，本次不动契约。
2. `candidate` 的 `kind` 取 `srflx` 时，契约未规定候选的 `foundation`、`related_address`（STUN 反射的本地地址）与过期时间字段，做完整 ICE 时需要补。
3. `answer.chosen_candidate` 为单值，无法表达「选中候选后又被替换」的场景；运行中从直连切中继目前只能靠新的 `session_start`，契约未定义切换信令。

## 五、直连能撑到什么画质

把两组实测拼起来看：

- **链路能力**：局域网直连在 38.1 Mbps（手机 Wi-Fi）与 39.94 Mbps（虚机 VMnet8）时仍然 0% 丢包，说明两条直连路径的可用带宽都明显高于 38 Mbps（本次只测到 40 Mbps 目标，未继续加压）。
- **1080p30 需求**：文字场景达到 SSIM ≥0.98 需要约 2.6 Mbps 媒体码率（对应线上约 3.5 Mbps）；静态桌面 1 Mbps 媒体即可到 0.9936；视频/拖拽场景 4 Mbps 目标下 SSIM 0.91–0.98。
- **结论**：直连跑 1080p30 的余量充足，建议直连默认档位 1080p30 @ 4 Mbps（线上约 5.4 Mbps），文字画面可稳定在 SSIM 0.99 以上。1080p60 与 1440p60 按同比例推算需要 5–16 Mbps，落在实测链路能力内，但**60 帧管线本次未实测**，不作为已验证结论。

**公网上限**：P2P 直连的真实上限由被控端宽带上行决定。本环境缺少公网接收端，无法实测上行带宽；这一项必须等 ECS 上的 STUN/TURN 端点就位后补测，报告中不做估算。

## 六、回落中继设计建议（只出设计，不动实现）

### 6.1 建立阶段

1. **候选收集**：并行向 2 个 STUN 服务查询，单个超时 800 ms，总预算 1.5 s；同时枚举 host 候选。取首个成功的 srflx 作为主候选，第二个用作对称型判定依据（映射地址不一致即判定对端/本端对称）。
2. **候选排序**：host（同网段）> srflx（锥形）> relay。本次实测支持该顺序：host 直连 100 ms 内打通且 38 Mbps 无丢包。
3. **连通性检查**：每对候选每 100 ms 发一个检查包（实测一个周期即可打通），单候选预算 2 s，整体预算 5 s。
4. **成功判据**：**双向**都收到 ≥2 个检查响应且 RTT 采样 ≥3 个；单向收到不算成功（本次同 NAT 场景出现了「一端能发、另一端收不到」的典型失败形态，必须双向确认）。
5. **并行预取**：候选检查进行到 2 s 仍未成功时，立即并行发 `relay_allocate`，避免失败后再多一个信令往返。

### 6.2 失败判定与重试

| 条件 | 处置 |
| --- | --- |
| 5 s 内无任一候选双向成功 | 判定打洞失败，切中继 |
| 检测到任一端为对称型 NAT（映射端口随目的变化） | 跳过打洞，直接 `relay_allocate`；本次实测该形态 16 s 内 0 包，继续重试无意义 |
| 同出口（双方 srflx 公网地址相同） | 优先 host 候选；若 host 也不通再考虑中继，不做公网回环尝试 |
| 原地重试 | 不做。同一映射重试无意义，只在新会话重建时最多重试 1 次 |
| 切换后再回切 | 不允许。切到中继后本会话不再回切直连，避免抖动 |

### 6.3 运行中降级

直连建立后满足任一条件，切中继并保持到会话结束：

- 连续 3 s 窗口丢包率 > 20%；
- RTT p95 > 300 ms 持续 5 s；
- 解码端连续 2 s 无可解码帧（对应本次公网中继实测中「连续丢包导致最长 2.0 s 不可解码」的现象）;
- 关键帧请求 3 次仍无关键帧到达。

切换时的码率档位直接取 `relay_allocated.budget_kbps` 与 `quality_profile`，不自行猜测。

### 6.4 与现有代码的衔接点

- 直连成功后 `session_start.transport_kind = "direct"`，`commands/service.py` 已按 `transport_kind` 放开直连档位，无需改判定。
- 回落时发新的 `session_start.transport_kind = "relay"` 并附 `relay_allocated` 结果，现有档位收敛逻辑可直接生效。
- 运行中切换需要契约补充（见 3.5 第 3 条），本次只记录。

## 七ter、三层技术路线与主场景覆盖

策略口径已单独成文：[docs/design/connect-v1.md](file:///c:/Users/Administrator/Desktop/RemoteDesktop/docs/design/connect-v1.md)（IPv6 → P2P → 中继，含参数表、伪代码与四端分工）。这里只给「手机在外控家里电脑」的覆盖结论。

| 主场景 | L1 IPv6 | L2 P2P | L3 中继 | 当前实际可用性 |
| --- | --- | --- | --- | --- |
| 手机移动数据 → 家里电脑 | 手机侧移动网络普遍有 v6（**未验证**，设备不在）；家里电脑无 v6（已实测） | **不可穿**：移动侧为对称型 CGNAT（已实测 0 包） | 可用 | **只有中继**，画质受 3 Mbps 限制 |
| 手机在家 Wi-Fi → 家里电脑 | 无 v6（已实测） | 同出口不做公网回环（已实测失败），走局域网 host 候选可直连 | 可用 | 直连（同网段）38 Mbps |
| 手机 Wi-Fi → 异地电脑（两端锥形） | 取决于双方 v6 | 具备条件，**未验证**（缺第二个锥形出口） | 可用 | 待补测 |
| 任意一端对称型 | 取决于 v6 | 不可穿（已实测） | 可用 | 中继 |

**家宽开通 IPv6 之后的预期**：手机在移动数据下可直接 v6 直连家里电脑，不需要打洞、不消耗服务器带宽；这是主场景唯一能拿到 1080p30 而不升级带宽的路径。前提是两端都拿到全局 v6，且手机侧运营商未做 v6 防火墙拦截（运营商 v6 入站策略**未验证**）。

**3 Mbps 中继到底能撑什么（实测，同一编码器、同一测试卡）**：

| 分辨率 | 内容 | 目标码率 | 媒体码率 | 线上码率 | SSIM | 文字区 SSIM | 解码 fps |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1080p30 | 静态桌面 | 2000 kbps | 2201 kbps | 2983 kbps | 0.9771 | 0.9744 | 29.06 |
| 1080p30 | 文字 | 2000 kbps | 2430 kbps | **3288 kbps** | 0.9750 | 0.9731 | 29.16 |
| 720p30 | 静态桌面 | 2000 kbps | 2109 kbps | 2861 kbps | 0.9943 | 0.9920 | 30.20 |
| 720p30 | 文字 | 2000 kbps | 2180 kbps | 2956 kbps | 0.9943 | 0.9920 | 29.82 |

证据：`evidence/quality-3mbps-1080p30/quality_result.json`、`evidence/quality-3mbps-720p30/quality_result.json`。

判读：在 3 Mbps 线上预算下，720p30 两种内容都能到 SSIM 0.99 以上并贴着预算（2.86–2.96 Mbps）；1080p30 文字场景线上要 3.29 Mbps 已经超预算，即使不超，SSIM 也只有 0.97。**「3 Mbps 只能 720p」有实测支撑**，不是估算。

**需要升级带宽的用户**：只走中继、且要求 1080p30 文字清晰（SSIM ≥0.98）的用户。按 1.36× 封装膨胀，1080p30 文字需要约 3.5 Mbps 线上，留 30% 余量则中继出口至少 5 Mbps/会话。若用户还有 v6，则不必升级带宽。

## 八、尚未验证项（明确列出，避免误读）

1. 锥形 ↔ 锥形（两端都是家庭宽带）的真实打洞成功率——ECS STUN 已就绪，但虚机与主机共用同一公网出口，仍缺第二个独立公网出口，**保持未验证**。
2. 公网直连的上行带宽上限——缺少公网接收端。
3. 1080p60 / 1440p60 直连管线——本次只测 1080p30。
4. 手机端 MediaCodec 解码帧率与延迟——Android 控制端当前固定请求 20 fps / 4500 kbps，且指标只进界面，未做与本次链路的联调。
5. IPv6 端到端直连（第一层）——两端均无全局 v6：本机与家宽已实测不可用，ECS 无 AAAA 记录且无登录凭据无法核对；手机侧移动网络 v6 待设备回来验证。
6. 运营商对 v6 入站的过滤策略——即便两端拿到 v6，移动网络是否放行入站需实测。
