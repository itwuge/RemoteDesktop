| 项 | 内容 |
|---|---|
| 适用对象 | 安卓被控端 / 控制端（正在把握手升级到 `hs=2`） |
| 桌面端实现 | `src/rdc/media/frame.py`（v2 编解码 + 版本协商） |
| 契约状态 | 新增消息类型属增量，正文未改；变更记录见 `.team/records/契约变更记录-契约-202611-011-20261110.md` |
| 本轮约定 | 桌面端默认协商 v2；v1 仅作兼容解码 |

## 1. 版本号与协商

1. 帧版本号是**媒体封装版本**，与握手版本 `hs` 是两件事：`hs=2` 只说明信道握手升级，帧版本仍由 `media_caps` 协商。请先完成 `hs=2` 握手，再按本文解析数据面明文。
2. `offer` / `answer` 的 `media_caps` 里新增数组字段：

   ```json
   "media_caps": {
     "codecs": ["h264"],
     "max_width": 1920,
     "max_height": 1080,
     "max_fps": 30,
     "frame_versions": [2, 1],
     "frame_version": 2
   }
   ```

   - `frame_versions`：本端支持的版本，**按优先级从高到低**；桌面端固定 `[2,1]`。
   - `frame_version`：`answer` 里的最终结论（由媒体生产方给出）；收到 `answer` 以它为准。
3. 协商规则：取双方交集里优先级最高的版本；交集为空、缺字段、版本号未知 → 一律按 v1 解析（兼容）。桌面端在降级时会打印“帧封装回退 v1, 带宽开销会上升”，不会静默回退。
4. 单个整数 `frame_version: 2` 也接受，等价于 `frame_versions: [2]`。

## 2. v2 帧格式（定长 28 字节头 + 原始 H.264 净荷）

- 大端（网络字节序），结构体格式串 `>2sBBIqHHII`。
- **没有 JSON、没有 base64**；`payload_len` 后面直接跟 H.264 码流字节。
- 上层仍是 AEAD 封套：先完成 AEAD 解密，得到的明文前 2 字节才是本格式的 magic。

| 偏移 | 长度 | 类型 | 字段 | 说明 |
|---:|---:|---|---|---|
| 0 | 2 | bytes | `magic` | 固定 `0x52 0x46`（ASCII `RF`） |
| 2 | 1 | u8 | `version` | 固定 `2` |
| 3 | 1 | u8 | `flags` | bit0=`FLAG_KEYFRAME`（关键帧），bit1=`FLAG_CRC32`（头部 CRC 有效），其余位保留为 0 |
| 4 | 4 | u32 | `seq` | 帧序号，从 0 递增，接收端用它判断丢帧 |
| 8 | 8 | i64 | `pts` | 编码时间戳（编码器输出的 pts，单位由编码器决定） |
| 16 | 2 | u16 | `width` | 画面宽（像素） |
| 18 | 2 | u16 | `height` | 画面高（像素） |
| 20 | 4 | u32 | `payload_len` | 净荷字节数，上限 8 MiB（`8388608`） |
| 24 | 4 | u32 | `crc32` | `crc32` 覆盖第 0–23 字节；`flags` 未置 bit1 时填 0，接收端忽略 |
| 28 | N | bytes | `payload` | 原始 H.264 访问单元（含 SPS/PPS，关键帧自带） |

接收端校验顺序（建议一致，便于对照错误码）：

1. 长度 < 28 → `FRAME_TRUNCATED`
2. magic 不是 `RF` → `FRAME_BAD_MAGIC`（但若走了分流规则，说明对端还在用 v1）
3. `version != 2` → `FRAME_UNSUPPORTED_VERSION`
4. `payload_len > 8 MiB` → `FRAME_TOO_LARGE`
5. 实际字节数 ≠ 28 + `payload_len` → `FRAME_LENGTH_MISMATCH`
6. `flags` 带 CRC 且校验失败 → `FRAME_CRC_MISMATCH`
7. 宽高为 0、`seq`/`pts` 越界 → `FRAME_FIELD_RANGE`

## 3. 分流规则（v1/v2 混跑期）

数据面明文：

- 前 2 字节 == `0x52 0x46` → 按上表解析 v2；
- 否则按 UTF-8 JSON 解析，`kind == "video"` 时是 v1：`{"kind":"video","codec":"h264","w","h","fps","key","pts","data":"<base64>","sent_ns"}`。

两条分支必须同时实现。协商结果为 v2 时不应再收到 v1 视频帧；收到说明对端实现有偏差，按 v1 解析即可，不要断链。

## 4. 逐字节样例

`seq=7, pts=42, 1920x1080, 关键帧, 净荷 5 字节, 带 CRC`：

```text
52 46 02 03 00 00 00 07 00 00 00 00 00 00 00 2a 07 80 04 38 00 00 00 05 0c ef 32 a7 | 00 00 00 01 67
└magic┘ ver flags └──seq──┘ └──────pts──────┘ └w──┘ └h──┘ └─len─┘ └─crc─┘   └─ H.264 净荷 ─┘
```

## 5. 错误码与处理建议

| 错误码 | 含义 | 建议处理 |
|---|---|---|
| `FRAME_TRUNCATED` | 明文不足 28 字节 | 丢弃该包，计数告警 |
| `FRAME_LENGTH_MISMATCH` | `payload_len` 与实际不符 | 丢弃该包；连续出现则断链重连 |
| `FRAME_BAD_MAGIC` | magic 不对 | 丢弃，转 v1 分支再试一次 |
| `FRAME_UNSUPPORTED_VERSION` | 版本号未知 | 丢弃并记录，等对端降级协商 |
| `FRAME_CRC_MISMATCH` | 头 CRC 校验失败 | 丢弃该包（头损坏，字段不可信） |
| `FRAME_TOO_LARGE` | 净荷超 8 MiB | 丢弃并断链（异常对端） |
| `FRAME_FIELD_RANGE` | 宽高/序号/时间戳越界 | 丢弃该包并计数 |
| `FRAME_BAD_PAYLOAD` | v1 JSON 字段类型不对 | 丢弃该包，计数告警 |
| `FRAME_KIND_MISMATCH` | 解析入口与消息类型不符 | 丢弃该包 |

## 6. 带宽口径（便于与桌面端对齐验收）

- 帧封装口径：每帧固定多 28 字节头，外层 AEAD 另加 4 字节长度前缀 + 12 字节 nonce + 16 字节 tag = **每帧约 60 字节**，与净荷无关。
- 端到端 wire/media：1080p30 约 1.007–1.009；720p10 @200 kbps 约 1.033（控制帧已降频）。
- v1 的端到端开销是 1.34–1.40，升级到 v2 是带宽收益的主要来源，请勿在安卓侧再包一层 base64。
