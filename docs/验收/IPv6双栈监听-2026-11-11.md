## 1. 结论

- 被控服务端口仍为 27888，监听从纯 IPv4 改为单 socket 双栈：IPv4 与 IPv6 字面量地址同时可达。
- 桌面控制端用 IPv6 字面量（`::1` 与本机 `240e:370:6303:cb0:8c94:c8d0:eb5b:cc5`）均完成握手并出画面。
- 未改 `desktop-v1` 契约命令，未改 UI 行为；候选交换、打洞、选路回退一律未触碰。

## 2. 方案选择：单 socket + `IPV6_V6ONLY=0`

选单 socket，不选双 socket，依据如下（Windows 侧为本机实测）：

| 事实 | 实测/依据 |
| --- | --- |
| Windows 的 `IPV6_V6ONLY` 默认值为 1 | 本机 `getsockopt(IPPROTO_IPV6, IPV6_V6ONLY)` 读到 `1` |
| 默认值 1 时 IPv4 不可达 | AF_INET6 + V6ONLY=1 绑 `::`，IPv4 连 `127.0.0.1` 超时失败 |
| 显式置 0 后同端口双栈可达 | 同一 AF_INET6 socket 置 V6ONLY=0 后，IPv4 与 IPv6 连接均被接受 |
| 双栈下 IPv4 来源呈现为映射地址 | 从 127.0.0.1 连入，`accept()` 得到 `::ffff:127.0.0.1`，`family=AF_INET6` |
| Linux 由 `net.ipv6.bindv6only` 决定默认值（发行版通常为 0） | 不依赖系统默认，代码显式置 0，两端行为一致 |

选择理由：

- 单 socket 只有一个 accept 循环、一份连接生命周期与一个端口，双栈语义清晰；
- 双 socket 需要两个 accept 循环，且 Linux 上若先绑 `0.0.0.0` 再绑 `::` 会因默认双栈触发 `EADDRINUSE`，必须先显式 `V6ONLY=1` 再排序绑定，复杂度更高；
- 双栈带来的唯一副作用是 IPv4 来源变成 `::ffff:a.b.c.d`，在 accept 处归一为 IPv4 即可，白名单、每 IP 限流与日志口径与单栈时完全一致。

## 10. 中继名额回收缺陷（2026-11-11，已在 1.0.0 修复）

**修复内容**

1. 清理改为定时器驱动：`InMemorySignalingServer.start_maintenance()` 每 15s 跑一次 `_purge_expired()`，不再依赖入站消息；随 `RelayServer.serve_forever()` 启动、`stop()`/`_shutdown()` 停止。
2. control 授予 TTL 可配置：新增 `RelayConfig.control_grant_ttl_s`（ini `[relay] control_grant_ttl_s`，默认 90），与 `challenge_ttl_s` 解耦；未新增契约命令。
3. 名额改按活跃连接计算：`_session_is_alive()` 要求会话参与设备都在线，控制端连接消失即释放名额，不再等授予过期。
4. 回归：`tests/test_relay_signaling_v12.py` 新增 3 项（断线释放名额、TTL 默认值与可配置、无入站消息也能定时清理）。
5. 门禁六项全绿（710 项通过，证据 `D:\RDC-Build\evidence\gate\20261111-045121`）。

**遗留（1.0.1）**：publisher 数据面心跳探活（5s×3）不做，当前限制为「控制端异常退出后，中继名额最多占用 90 秒」，已写入发行清单第 10 节。

**原始登记（现象与机制，供回溯）**

**现象**：控制端被 force-stop 杀掉后 publisher 收不到优雅关闭，该会话继续挂在被控端中继里，后续连接 `relay_allocate` 返回 `RELAY_FULL: 中继通道已满`，直到旧授予过期。

**现状机制（已核实）**

- 会话名额只看「未过期的 control 授予」：`_handle_relay_allocate` 在 `signaling/server.py` 用 `relay_grants` 里 `expires_at > now` 的会话 ID 去重计数，超过 `max_sessions` 即拒绝。被控端 `HostConfig` 的 `max_sessions=2`（`src/rdc/session/host.py:477`），故两条残留会话即可占满。
- 授予 TTL 固定 `challenge_ttl_s=300`（修复前；`signaling/server.py:150`），`RelayGrantRecord.expires_at` 在签发时写死，**不随数据面活动续期**。
- 回收有三条：`_purge_expired()`（`signaling/server.py:868`）清过期授予；`ended=False` 且 `idle > SESSION_IDLE_TTL_S=300s` 且无有效授予的会话被 `_end_session`；数据面按 `grant.expires_at` 关会话（`relay/dataplane.py:299`）。`_purge_expired()` 只在 `handle()` 收到入站消息时执行，没有定时器。
- 因此残留会话的**最长占用约 300 秒**，随后自愈；被控端侧 `session_end` 依赖数据面报错，UDP 无回执时不会及时触发。

**结论**：`budget 8000` 不是被字节占满，而是「一路 control 会话」占住了名额（8000 是 `REQUEST_KBPS`，节点单路预算 9200）。真正的缺口是**回收粒度是 5 分钟且依赖入站消息触发**，杀客户端后的窗口内新连接一律 `RELAY_FULL`。

**建议落点（不改代码，待排期）**

1. 中继层（首选）：给 publisher 加数据面心跳（如每 5s 一次，连续 3 次缺失即吊销该会话授予），把回收依据从「授予 TTL」改成「真实活动」。
2. 中继层（低成本）：`_purge_expired()` 改为定时器驱动，`challenge_ttl_s` 的 control 授予单独下调到 30–60s 且可配置。
3. 不建议依赖 host 侧踢：host 自身可能先失联，且它拿不到控制端是否还活着的事实。

**版本判定**：属于可用性缺陷（最多 5 分钟不可连，可自愈），不是数据正确性问题。建议 1.0.0 只做第 2 条（低风险，改阈值+定时器）；第 1 条心跳进 1.0.1。若 1.0.0 已冻结，则整体登记 1.0.1，并在发布说明写明「控制端异常退出后最多 5 分钟内中继不可用」。

**复现**：正常建立中继会话 → force-stop 控制端 → 5 分钟内新连接 `relay_allocate` 必现 `RELAY_FULL`；重启被控端进程立即恢复（本轮即以此恢复）。
