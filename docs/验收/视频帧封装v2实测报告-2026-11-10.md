## 1. 实现

新增 [frame.py](file:///c:/Users/Administrator/Desktop/RemoteDesktop/src/rdc/media/frame.py)：

- `encode_v2` / `decode_v2`：28 字节定长二进制头 + 原始 H.264 净荷，不做 JSON、不做 base64。
- `decode_v1`：保留 `{"kind":"video","data":<base64>}` 解码兼容，旧客户端仍可读。
- `decode_frame`：按前 2 字节 `RF` 自动分流 v2 二进制帧与 v1 JSON 帧。
- `negotiate_frame_version`：读 `media_caps.frame_versions`，双方取最高共同版本，缺省或未知版本降级 v1。

### 1.1 v2 定长头（28 字节，大端 `>2sBBIqHHII`）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | magic | `b"RF"` |
| 2 | 1 | version | 固定 2 |
| 3 | 1 | flags | 位 0 关键帧；位 1 CRC32 有效；其余保留 |
| 4 | 4 | seq | 无符号 32 位 |
| 8 | 8 | pts | 有符号 64 位 |
| 16 | 2 | width | 无符号 16 位 |
| 18 | 2 | height | 无符号 16 位 |
| 20 | 4 | payload_len | 无符号 32 位 |
| 24 | 4 | crc32 | 可选；未置位时为 0 |

口径说明：

- **帧封装口径** = 序列化帧 + 4 字节长度前缀 + 12 字节 nonce + 16 字节 AEAD tag，不含 ping/pong 等控制帧。
- **wire/media** = 控制端数据面真实入站字节 ÷ 收到的媒体净荷字节，含控制帧与握手，是端到端口径。

## 4. 目标判定

| 判据 | 结果 | 结论 |
|---|---|---|
| 1080p30 wire/media ≤ 1.05 | 1.013–1.034 | 达成 |
| 1080p30 帧封装比 ≤ 1.05 | 1.007–1.019 | 达成 |
| 720p10 帧封装比 ≤ 1.05 | 1.0224–1.0244 | 达成 |
| 720p10 wire/media ≤ 1.05 | 1.033（控制帧降频后，见 §11；改前 1.061–1.066，原始 1.076–1.083） | 达成 |
| 画质不低于 v1 | ΔSSIM −0.00107 ~ +0.00629，静态与 720p 完全一致 | 达成 |

720p10 端到端原先未达 1.05 的原因：8 秒内媒体只有 201–220 kB，而 ping/pong 与握手的固定控制开销约 11.7 kB，占媒体 5.3%–5.8%。对比 1080p30 静态：控制开销同样是约 11.7 kB，但媒体 764 kB，占比仅 1.5%。也就是说，**差在低码率下控制帧占比被放大，不在帧头**；v2 帧封装本身已到 1.022–1.024。本轮已把控制探测降频并去掉冗余字段，720p10 实测降到 1.033（见 §11）。

极小帧另有固定头下限：150 B 净荷时 v2 wire 约 210 B（1.40×），仍显著低于 v1 的约 366 B（2.44×），但不可能压到 1.05。

## 5. 画质

- 静态桌面与 720p10 两档：v1/v2 的 SSIM、PSNR 逐位一致（0.99011 / 0.99177），因为封装层不改变净荷。
- 文本：0.98876 → 0.98884（+0.00008）。
- 视频：0.99177 → 0.99070（−0.00107）。
- 拖动：0.94199 → 0.94828（+0.00629）。

这些差异来自两次独立运行的编码器码率控制抖动，不是封装损失：单测 `test_v2_roundtrip_preserves_fields` 已证明 `decode_v2(encode_v2(frame))` 与原始 `VideoFrame` 完全相等。

快速拖动 4000k 的两次运行遇到并发负载，出现 8%–35% 丢帧，数据不可用，已从结论中剔除；上表改用无丢帧的 2000k 对照。该 4000k 运行仅保留在证据里，wire/media 仍为 v1 1.348、v2 1.007。

## 6. CPU 开销

- 发送路径（JSON 序列化 + base64 + AEAD + socket 写入）p50：静态 0.213→0.169 ms、文本 0.266→0.171 ms、拖动 0.384→0.220 ms、720p 静态 0.237→0.194 ms、720p 文本 0.205→0.151 ms，多数下降 18%–43%。
- 视频播放场景 0.252→0.273 ms（+8%），解码 0.861→1.090 ms，属于同机并发门禁/单测造成的测量噪声；其余解码 p50 为下降或持平（0.816→0.736、0.824→0.713、0.955→0.823、0.467→0.451）。
- 结论：v2 去掉 base64 与 JSON 解析后发送侧 CPU 稳定下降；解码侧没有系统性上升。上表数值在并发负载下采集，只作方向性判断。

### 11.1 控制类消息缩短 + 自适应降频（改前/改后实测）

只动验收装置的数据面探测，产品数据面本来就没有 ping/pong：

- 消息体：`{"kind":"ping","seq":n,"sent_ns":...}` → `{"kind":"ping","seq":n}`；`{"kind":"pong","seq":n,"recv_ns":...}` → `{"kind":"pong","seq":n}`。两端都不读这两个时间戳（控制端用本地 `perf_counter_ns()` 计时），单条约省 40 字节。
- 频率：固定 20 次/秒 → 有媒体在流时 2 次/秒（`RTT_ACTIVE_INTERVAL_S=0.5`），1 秒内无媒体帧时 1 次/秒（`RTT_IDLE_INTERVAL_S=1.0`）。理由：媒体帧在流时本身已证明链路活跃，20 次/秒的心跳式探测是纯浪费。
- 与心跳合并：数据面不再维护独立心跳，RTT 探测即保活；信令侧 10 秒 heartbeat 不变（不占媒体带宽）。

720p10 @200 kbps、同机同内容 8 秒窗口，三次运行对比（`evidence/frame-v2-720p10-ctrl-before|after`）：

| 场景 | 配置 | wire 字节 | wire/media | 帧封装比 | 控制字节 | 控制占比 | ping 次数 | RTT p50 / p95 (ms) |
|---|---|---:|---:|---:|---:|---:|---:|---|
| 静态 | 原始（20 Hz + 冗余字段） | 218,101 | 1.083 | 1.0244 | 11,700 | 5.8% | 160 | — |
| 静态 | 改前（20 Hz，去冗余字段） | 214,857 | 1.066 | 1.0244 | 8,440 | 4.19% | 135 | 0.77 / 2.22 |
| 静态 | 改后（自适应 2 Hz） | 208,216 | **1.033** | 1.0244 | 1,799 | 0.89% | 15 | 1.00 / 1.15 |
| 文本 | 原始（20 Hz + 冗余字段） | 236,337 | 1.076 | 1.0224 | 11,700 | 5.3% | 160 | — |
| 文本 | 改前（20 Hz，去冗余字段） | 233,006 | 1.061 | 1.0224 | 8,438 | 3.84% | 134 | 0.81 / 1.91 |
| 文本 | 改后（自适应 2 Hz） | 208,166 | **1.033** | 1.0244 | 1,800 | 0.89% | 15 | 0.76 / 1.04 |

结论：低码率端到端膨胀 1.076–1.083 → **1.033**，达到 ≤1.05；控制流量 11.7 kB → 1.8 kB（8 秒），控制占比 5.3%–5.8% → 0.89%。丢帧仍为 0，解码帧率 10.16–10.19 fps 不变（目标 10）。

代价与阈值依据：

- RTT 采样从 133–135 次降到 15 次；回环 p50 0.76–1.00 ms 仍在噪声量级，p95 反而从 1.9–2.2 ms 降到 1.0–1.2 ms（控制消息少了，排队更少）。
- 断线检测时效从最快 50 ms 变成最慢 1 秒。产品侧不依赖数据面 ping 判活：数据面 socket 超时 300 秒，信令 heartbeat 10 秒，二者都远大于 1 秒；验收装置若未来要用探测判活，1 秒也小于任何合理的 5–10 秒阈值。代价仅限于“RTT 曲线分辨率下降”，不影响可用性。
